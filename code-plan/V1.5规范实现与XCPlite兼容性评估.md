# 按 ASAM V1.5 规范实现 TCP master，能否兼容 XCPlite slave？

结论先行：**核心帧格式层面完全兼容（V1.5 §4.3 的 LEN+CTR LE16 头就是 XCPlite 的头）；但"严格照规范文本实现、不做任何适配"会在若干边角上碰壁。兼容性真正的瓶颈不在规范 vs XCPlite，而在你们 ECU 集成层的 CONNECT 后沉默异常。**

## 一、逐层判定

### 1. 传输帧头 —— ✅ 天然一致
- V1.5 §4.3.1：Control Field = LEN(WORD Intel) + CTR(WORD Intel)，且明文 "The same XCP Frame format is used for the stream oriented protocol TCP/IP"。
- XCPlite `tXcpCtoMessage{u16 dlc; u16 ctr}` packed（xcpEthTl.c:51-57），编译期强制头长 4 字节（xcpEthTl.c:33-36 #error）。
- **ECU 实测已验证**：`02 00 00 00 FF 00` 得 CONNECT RES；raw `[Len][CMD]` 裸流则 slave 把 0x01FF 当长度阻塞凑包。
⇒ 按规范做头，XCPlite 认。这一层零风险。

### 2. Tail/FILL —— ⚠️ 双向都有坑，需取交集策略
规范：单消息成帧 tail 可选（§4.3.2.1）；多消息拼接才要求 PACKET_ALIGNMENT_x（§4.3.2.2）。
- **master→slave 方向**：若严格按"单消息可无 tail"发不补齐帧（如 dlc=5 就发 9 字节），XCPlite 能收（rx 按 dlc 读 payload，xcpEthTl.c:335）。但若你拼段发送多个命令并加 FILL，XCPlite rx **不消费 FILL** ⇒ 流错位（D2）。
  ⇒ 兼容做法：**每帧只装一个 XCP 消息，且 payload 补齐到 4 字节边界**（FILL 内容 do-not-care）。补了 FILL 而对方不吞会怎样？——不会：XCPlite 只按 dlc 读 payload，剩余 FILL 留在内核缓冲……等等，这正是要点：**XCPlite 不吞 FILL，所以 master 干脆别发 FILL**。实测我们的脚本发补齐帧 + 读时吞填充，双方工作正常——因为 slave 发 CRM 从不带 FILL（size+4 精确，xcpEthTl.c:195），而 slave 收侧按 dlc 读取、我们发的 padding 恰好被下一次 4 字节头 recv 吃掉了吗？不是——padding 会被当成下一帧头！脚本实测成功说明：slave 对"多余字节"的处理是把它们读进下一个 msgBuf.dlc 位置……实际观察是每条命令独立应答、会话连续无错位，证明**定长补齐帧在 XCPlite 上是安全的**（它每次读 4+dlc，我们发 4+ceil4(dlc)，差值字节进入下一次头部读取——这正是本地假服务器要求"接收方必须吞填充"的同款问题，只是 slave rx 循环容忍了我们，因为我们的 padding 全 0 且下一条真实帧头恰好重新对齐……此点存疑，落地前用 libxcp 联调抓包复核一次）。
  ⇒ 保守推荐：**payload 不补齐（dlc 即真实长度）**，与 XCPlite 自身 TX 行为对称（它也从不发 FILL）。这是双方都绝对安全的最小公倍数。
- **slave→master 方向**：XCPlite CRM 无 FILL ⇒ 你的接收器按 4+dlc 读取即可；但为兼容其他严格规范实现的对端，接收器仍应吞掉 `(4-dlc%4)%4` 填充（规范允许 tail 存在）。

### 3. CTR 语义 —— ✅ 一致
§4.3.1.2：master 每包递增（不分类型）、multicast=0；slave 独立计数器覆盖全部类型。XCPlite 单 `gXcpTl.Ctr++` 全类型递增（xcpEthTl.c:190, xcpQueue64.c:707）——字面合规。你的实现只需：同连接内 CRO CTR 逐命令 ++；不要校验/依赖 slave CTR 连续性之外的东西（丢包补偿会让它跳号）。

### 4. 会话模型 —— ✅ 一致 + 一条纪律
§4.1.1 单连接、FIN 触发 XCP disconnect：XCPlite 均实现（accept 仅当 Sock INVALID；n==0 → XcpDisconnect）。
⚠️ 纪律：因 XCPlite 的 backlog=5 排队行为（D1），**你的 TcpTransport 析构/超时/错误路径必须显式 close socket**，否则重连会假死在 accept 队列里。规范没义务提醒你，但这是事实约束。

### 5. §5 以太网专有命令 —— ✅ 规范授权静默，但你要能忍
GET_SLAVE_ID 等五个子命令全部 optional，规范明文"可能连负响应都不发"。XCPlite 默认编译（多播宏关）确实全静默。
⇒ 按规范实现的你如果**依赖**这些命令做任何流程（slave discovery、时钟同步），会失败——不是不兼容，是功能不可达。设计上直接跳过 §5。

### 6. 基础标准差异 —— ⚠️ 两处要留意
- XCPlite 协议层版本 **1.2**（xcp_cfg.h:28）：不支持 GET_DAQ_LIST(0x76)/GET_ODT(0x75)/GET_DLP 等新查询命令（switch 无 case → ERR CMD_UNKNOWN 0x20），也不支持 prepare-for-start mode 3（0x0104 特性，代码有分支但版本宏未到）。A2L 驱动的 master 若对这些命令做能力探测要按 ERR 处理，不能假设支持。
- CONNECT RES 的 RESOURCE=0x05/COMM_BASIC=0x80 硬编码（D5）：能力位不可信，以命令试错为准。
- 未连接发非 CONNECT 命令：XCPlite 静默丢弃（D6）而非回 CMD_IGNORED——你的 master 状态机要把"无响应"当作合法结果处理（超时分类，勿重试风暴）。

## 二、决定性提醒：以上都不是当前拦路虎

ECU 实测矩阵（m00304/m00440）：CONNECT 之后的**任何**命令（包括 stock XCPlite 必须回 ERR 的未知命令）全部沉默。这个行为既不合规也不合库源码——它是 ECU 集成层异常（第 7 节三选一待裁决）。
⇒ **即使你把 libxcp TcpTransport 按 V1.5 完美实现，接上这台 ECU 依然只会拿到一个 CONNECT RES，然后超时。** 先解决集成问题（ECU 侧日志/tcPdump 裁决），TcpTransport 才能进入真实联调。设计本身可以并行推进——它对"标准 XCPlite slave"（如本机跑 cal_test/daq_test 示例）应当开箱可通，这可以作为开发期的验收靶子。

## 三、给 libxcp TcpTransport 的兼容性配方（最终版）

| 项 | 取值 | 依据 |
|---|---|---|
| 头 | `<HH` dlc+ctr LE16 | §4.3.1 = XCPlite，实测 |
| TX payload | 不补齐，dlc=真实长度 | 与 XCPlite TX 对称，最小公倍数 |
| RX | 读 4B 头 → 读 dlc B → 吞 `(4-dlc%4)%4` FILL（限时 0.5s，超时不视为错误） | 兼容严格规范对端；对 XCPlite 无害（它不发 FILL，吞不到东西） |
| CTR | 本连接逐命令 ++；重连重置 | §4.3.1.2 |
| PID | 0xFF RES / 0xFE ERR(code=payload[1]) / 0xFD EV / 0xFC SERV / ≤0xFB DTO | 基础标准 |
| 连接管理 | 单连接；所有退出路径显式 close | §4.1.1 + D1 |
| §5 TL 命令 | 不实现、不依赖 | 规范 optional + XCPlite 不可达 |
| 能力探测 | 按 ERR 0x20 降级；RESOURCE 位仅参考 | 协议层 1.2 + D5 |
| 超时语义 | 无响应 ≠ 链路故障（可能是被忽略） | D6 |
