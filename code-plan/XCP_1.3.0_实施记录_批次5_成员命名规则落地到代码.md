## 2. 执行方法：先判定安全性，再动文件

不做"按字段名全局文本替换"。改为**按标识符的全部持有者**分流：

| 判定 | 含义 | 数量 | 处理 |
|---|---|---|---|
| SAFE | 该标识符的所有持有者都属于待改名 struct | 判定 56 / 57，**实际成立 55** | 词边界整体替换（`\bname\b`） |
| CONFLICT | 存在 class 持有者或非目标 struct | 识别出 1，**实际有 2** | 逐点判定接收者类型后手工改 |

> ⚠️ 上表的"实际成立 55 / 实际有 2"是收尾复查（§3.7）后才修正的：`m_byte_order_` 本来就是
> 第 2 个 CONFLICT（`struct ConnectResponse` + `class CommandCodec` / `class ResponseParser`），
> 但两个 class 的声明因检测器盲区 ① 从未被登记，"全部持有者"检查于是**空洞地通过**。
> 一条判定的强度不超过它所依赖的解析器的完备度——这是本批次最贵的一课。

**当时识别出的 CONFLICT：`m_error_code_`** —— 同时是 `struct NegativeResponse` 与 `class XcpException` 的成员。
在 `include/`+`src/`+`tests/` 共 13 处出现，逐处读出 `err` 的声明类型后：

- 改 10 处（9 行；`command_executor.cpp:33` 一行两处）：`protocolMessage(..., const NegativeResponse& err)`、
  `std::get_if<NegativeResponse>(&...)`（executor 2 处、test 2 处）、`NegativeResponse err;`（parser）
- 留 3 处：`xcp_error.hpp:81` 声明、`xcp_error.cpp:41` 构造初始化列表、`xcp_error.cpp:52` getter

`m_data_` 分属 4 个 struct（`PositiveResponse`/`ServicePacket`/`DtoPacket`/`UdpFrame`）但 4 者都是待改名
struct，故属 SAFE；跨类同名风险已由"全部持有者"判定覆盖，不依赖人工记忆。

### 四道防呆（前三道当时实际发挥作用，第四道是收尾复查补上的）

1. **struct/class 跨界检查**：class 侧改名前必须先确认目标标识符不被任何 struct 持有 → 实测"无跨界冲突"才放行。
   ⚠️ 收尾复查证明**这道防呆没起到它应有的作用**：它的输入来自同一个有盲区的解析器（§3.7），
   所以"`m_byte_order_` 不被任何 class 持有"是一个基于**残缺数据集**得出的真命题式假结论。
   防呆的有效性不超过其数据源；同源的检查等于没有检查。
2. **改名后同 struct 内重名检查**：曾报出 `max_cto` / `max_dto` 与测试侧 `AgCase` 既有裸名字段趋同。
   判定为**不同作用域、无害**，但要求显式确认而非默认放行。
3. **零命中即中止**：`rename_struct_fields.py` 若对待改名 struct 命中 0 字段则直接 `SystemExit`。
   这条在本批次**真的拦住了一次**：首版把 `own` 的键（字段名字符串）当元组用 `k[1]` 取，
   得到"SAFE 0 / CONFLICT 0"——正是上次审核中我踩过的"0 命中未证伪就当真"的同一类错误。
   但注意：它只防"**全零**"，防不了"**少报**"，盲区 ① 恰恰是少报。
4. **改动前基线逐条映射核对**（收尾复查补上，`verify_rename_baseline.py`）：不依赖改后检测器，
   而是拿改动前快照对每个成员核验"前名 → 后名"是否落在规则允许的四种映射之内，
   并要求该核对自身带 6 项灵敏度自测（注入错误必须被报出）。这道防呆才是最终抓住误改的那一道。

### class 侧词法安全性说明

`\bm_memory\b` **不会**匹配 `m_memory_` 内部（下划线是单词字符），故补尾下划线不会与
`UdpTestSlave::m_memory_` 等既有合规成员互相污染；替换用**单趟** `re.sub` + 字典映射，
避免 `m_ag → m_ag_` 之后被二次加工成 `m_ag__`。

审计口径差异已核实：class 侧 44 条记录 vs 42 个唯一 (类名, 成员) 对，差额 2 来自
**两个同名但独立的 `EventRecorder` 类**（`xcp_udp_loopback_test.cpp:123`、
`xcp_master_integration_test.cpp:49`），各有 `m_events` / `m_cmd_pending`。非解析缺陷。

### 3.7 收尾复查发现并修正的问题（本节是本轮"查漏"的产出）

用户要求复查是否有遗漏后，用三项独立手段交叉检查，**确实查出真遗漏**：

| 手段 | 结果 |
|---|---|
| **孤儿标识符核对**：代码里每个 `m_*_` 名字必须能被检测器归属到某个 class 成员 | 4 个归不进去 → 顺藤摸出检测器的 4 个盲区（下表） |
| **独立暴力复核**：不复用主检测器，自己数括号找 `struct` 体内是否残留 `m_` 声明 | 0 处 ✅（证明 struct 侧改名确实彻底） |
| **测试标识符比对**：与改动前快照逐一比对 `TEST`/`TEST_F`/`TEST_P` 用例名 | 227 = 227，完全一致 ✅（改名未波及任何用例名） |

#### 检测器的四个盲区（这是本批次真正的根因）

| 盲区 | 成因 | 后果 |
|---|---|---|
| ① `private:` / `public:` 后的**首条**成员声明 | 访问说明符不与下一条语句分隔，粘连后整条被丢 | **每个访问说明符块少报 1 条成员**，共漏 20+ 条 |
| ② `#if defined(_WIN32)` 粘连 | 指令行的圆括号使该声明被误判为函数 | `RawSender::m_wsa_ok_` 等漏记 |
| ③ `decltype(::socket(...)) m_handle_{}` | "语句含括号即函数"的粗判 | 类型含括号的数据成员全部漏记 |
| ④ `#endif` | 被当成标识符 | 产生名叫 `endif` 的**假成员**（多报） |

修正后：合成用例 9/9、语料锚点全中，成员记录总数由 207 增至 **230**（含此前漏记的 23 条），
文档侧由 123 增至 130。**修正只改变统计口径，未新增任何违规**——23 条新可见成员里
20 条本就合规，**3 条是真实违规**（见下）。

#### 由此查出的真实遗漏：2 处误改 + 3 处漏改

| 类别 | 位置 | 详情 | 处置 |
|---|---|---|---|
| **误改（本批次自伤）** | `CommandCodec::m_byte_order_`、`ResponseParser::m_byte_order_` | 二者都是 `private:` 后首条 → 从未进入"全部持有者"判定 → `m_byte_order_` 被误判为"只属于 `struct ConnectResponse`"，class 侧被连带改成裸名。**声明与引用同步改掉，编译器发现不了**；设计文档 §4/§5 一直写的是 `m_byte_order_`，是我偏离了文档 | 逐点精确回退（9 个位置：2 处声明 + 4 处 `command_codec.cpp` + 3 处 `response_parser.cpp`；构造函数**形参** `byte_order` 与 `ResponseParser` 里 `resp.byte_order` 这个 struct 字段访问必须保持裸名，故不能整体替换） |
| **漏改** | `ThreadJoiner::m_thread`（`recovery_test.cpp`、`xcp_master_integration_test.cpp` 各一个同名类）、`ScriptedSlave::m_responses` | 同类成员，因盲区 ① 漏记 → 改名脚本没轮到它们 | 补齐尾下划线，共 12 处词边界替换；改前确认这 3 个标识符**不与任何 struct 字段同名** |

修正后又用 `verify_rename_baseline.py` 做**改动前快照 → 现状**的逐条映射核对：
222 个 (类别, 类型, 成员) 三元组全部落在规则允许的四种映射之内，0 违规、0 意外新增。
该核对自带 6 项灵敏度自测（注入"class 被改成裸名 / struct 漏改 / 本应保留的成员消失 /
新旧名并存 / 凭空新增"五种错误），**首轮自测即抓出我核对逻辑自身的漏洞**——
"struct 漏改"会因"快照有、现状也有"被误判为合规未变，据此把判定拆成
"本就不该改"与"应当改名"两条分支后 6/6 通过。

#### 本批次最重要的一条方法论

> **改名脚本与审计脚本共用同一个解析器时，解析器的盲区会同时污染"执行"与"验证"两端**，
> 形成"用同一把坏尺子量自己"的闭环，表现为：改得对（编译器过）、量得也对（自检过），
> 但结论是错的。打破方式只有一种——引入**改动前的独立基线**做逐条映射核对，
> 并要求该核对自身带灵敏度自测。
