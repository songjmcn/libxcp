# XCP on TCP：A2L 与线路证据联合决策两阶段计划

状态：**第一阶段总体设计已分节确认；选择逻辑、A2L 扫描器和受控快照已实现并接入 `xcp_master`；本机因无可证明的私人目录，A2L 正向 alignment 仍不可达（失败关闭已实测）；第二阶段提取仍须评审**  
范围：先在 `xcp_master` 验证决策逻辑，再提炼可复用组件。用户已要求按计划实施；具体实现必须遵循已确认的约束和评审门禁。

## 1. 目标与非目标

### 1.1 目标

- 使用对应 TCP 端点的 A2L 静态事实、用户显式配置及运行时 TCP/XCP 证据，形成可解释的连接配置决策。
- 将“配置来源”“试连成功”“线路行为相容”“有足够证据唯一确认”区分展示；不得把 CONNECT 成功表述成协议版本或 alignment 已识别。
- 第一阶段在 `xcp_master` 完成并验证逻辑；第二阶段在保留第一阶段语义的前提下，抽离与 UI 和 A2L 文件解析无关的复用组件。
- PL 版本、TL 版本、Wire Profile、alignment 分别记录；本项目 `AsamV14` 是以 XCPlite V1.2 为基线的兼容标签，不泛化为所有 TL 1.4 实现。

### 1.2 非目标

- 不声称仅凭 A2L 和嗅探总能唯一确定真实设备配置；不以首帧、接收分片边界、填充值或超时推断 Tail。
- 不在同一 TCP 连接中切换 Profile/alignment，不静默重连或自动修改运行中配置。
- 不更改 UDP 行为，不增加 IPv6、TLS、自动恢复或生产级 TCP Slave。
- 不以自有 mock 或 XCPlite V1.2 结果声称通过 ASAM V1.5 全面一致性认证。
- 不假设 CANape 的实现机制，亦不保证完全复制其行为。

## 2. 基线及问题

1. `tools/xcp_master/transport_selection.hpp` 已接收 A2L TCP 端点、alignment 声明和 PL/TL 信息。显式 V15 使用 CLI 或 A2L 对齐；当前 auto 分支不校验 A2L 对齐。
2. `src/tcp_framing_negotiation.cpp` 默认按 V14/8、V15/8、V15/16、V15/32 顺序试连，首个成功即返回；`tools/xcp_master/main.cpp` 当前按 CONNECT 和有限字段判定。该行为是启发式试连，不是唯一识别。
3. `include/libxcp/tcp_wire_profile.hpp` 冻结连接的 Profile，并禁止根据 PL/TL、alignment 或首帧单独推导 Profile；本计划保持连接不可变原则。若调整 auto 的用户可见语义，须明确记录其与历史计划及 CLI 的兼容关系。
4. `thirdparty/a2llib/src/xcp/xcpontcpip.cpp` 对非法 alignment 字面量可能保留默认值或旧值但标记已声明；声明标志不能证明输入有效。实施前需验证并确定可信事实获取方式。禁止未经明确指示修改 `thirdparty` 中非 `thirdparty/a2l-sdk` 的文件；不可通过跳过校验将非法值当成有效 8 bit。
5. V1.5 规范 §4.3.2 单消息 Tail 可选，多消息填充字节内容无约束；TCP 为字节流。当前 V15 decoder 的固定 Tail 消费与不同发送组合的互操作边界须专门验证，不能仅凭成功试连作结论。
6. 静态审查提示 `src/tcp_stream_decoder.cpp` 的 `Finish()` 在完整头之后零 payload 即 FIN 时可能漏判截断；这是待测试验证的独立问题，不预设已复现或自动纳入本计划修复。

## 3. 证据与决策原则

### 3.1 证据模型

- **用户配置**：保存 Profile、alignment、端点、PL/TL 的显式值及来源；配置的优先级不等于其与设备事实必然一致。
- **A2L**：匹配 TCP transport 和目标端点；保留来源、版本原值、alignment 的有效/缺失/无效/冲突状态。端点不唯一或事实冲突时不得静默选一个。
- **线路观察**：仅记录真实观察到的响应、报文解析结果、版本响应和可复现的矛盾；不能把时间间隔、单次 `recv()` 或 FILL 内容当作边界依据。
- **证据强度**：显式配置是选定策略，A2L 是静态声明，试连成功只说明观测范围内相容。只在证据能排除其他候选且语义成立时使用“唯一确认”。PL/TL 报告值与本地 Profile 分开展示。

### 3.2 结果分类与默认安全策略

| 结果 | 含义 | 建议处理 |
|---|---|---|
| 已配置，待验证 | 显式配置或可信 A2L 形成候选，但尚无运行时证据 | 输出来源，不声称识别 |
| 已验证相容，仍有歧义 | 当前观察可由多个候选解释 | 默认提示用户指定；若另选兼容模式，须显式启用并记录风险 |
| 证据支持唯一候选 | 定义明确的观察足以排除其他候选 | 固定配置，保留可审计证据；不能推断未观察到的功能 |
| 冲突 | 对端观察与声明或固定配置矛盾 | 停止当前会话并报告，禁止连接内切换 |
| 无效、缺失或不可用 | 输入无效、端点不唯一、无响应或超时等 | 按具体原因报错，不误报为对端不支持某个 Profile |

用户已确认：显式配置与可比的 A2L 声明冲突时采用用户配置并报告双方值与来源；`--tcp-profile auto` 默认遇到无法排除的歧义时停止，旧首成功行为仅在显式 `--tcp-profile auto-legacy` 时启用，须警告非唯一识别和 ECU 会话副作用。试连超时、网络错误、设备拒绝或未观察到区别性填充均不能证明候选不支持。

### 3.3 连接和副作用

- 在线验证采用固定候选和有界超时；若需要尝试其他候选，关闭旧连接并创建新连接，明确提示试连可能影响从站会话状态。
- 禁止依靠异常吞掉错误后把所有失败都解释为“不支持”；分别报告连接失败、超时、XCP 错误、协议异常及配置冲突。
- 优先只使用用户允许的低风险操作；主动额外探测命令及其对目标设备的影响需单独评审，不默认发送写入、DAQ 配置或改变 ECU 状态的命令。
- 明确失败时清理连接和资源；不记录敏感 payload，诊断保留 transport、端点、候选、来源、阶段、原因。

## 4. 第一阶段：`xcp_master` 完成并验证

### 4.1 工作项

1. **输入与可信度核验**：盘点现有 A2L/bridge 输出，确认端点匹配、多实例、alignment 无效值如何可靠区分；若现有接口无法提供有效性，先提出依赖处理方案并征求授权，不能伪造可信状态。
2. **候选决策**：在应用连接选择流程中合并用户配置与可验证 A2L 事实，形成候选及来源；不得由 TL 或 alignment 单字段直接推出 Profile。明确 CLI 与 A2L 冲突策略。
3. **运行时验证**：在现有固定候选、独立连接机制上，区分连接成功、XCP 语义相容和可区分的线路证据；对于等价候选返回歧义，禁止首个 CONNECT 成功就称“确定”。
4. **诊断与交互**：在 CLI/TUI 显示端点、用户配置、A2L PL/TL/alignment、候选、来源、尝试结果、歧义及冲突；明确重试可能产生会话副作用。
5. **保持边界**：TCP 解码仅按固定配置工作，XCP 核心只提供会话事实；不把 A2L 文件解析和 UI 依赖注入 transport 或核心。
6. **记录**：更新用户帮助、兼容说明与 `code-plan` 实施记录，注明真实互操作设备、测试结果及未验证范围。

具体函数/文件改动以实施前阅读现有接口、设计评审和测试结果为准，不预先承诺新增公共 API。发现已有独立 decoder 缺陷时先编写复现和影响分析，修复范围另行确认。

### 4.2 第一阶段测试与验收

- **事实表驱动**：TCP/UDP 同文件、多个 TCP 端点、CLI/A2L 冲突、alignment 8/16/32、缺失、非法、重复声明、无法确定有效性，以及 PL/TL 分离；若依赖层无法识别非法声明，必须暴露失败或限制，不得用默认 8 充当有效结果。
- **歧义门禁**：V14/8 与 V15/8 字节等价样本；CONNECT 成功但后续出现可区分行为的样本；多个 alignment 在观测窗口无填充差异的样本；这些均不得报告已唯一识别。
- **线路边界**：分片、合包、任意值 FILL、LEN 内/外填充、可选 Tail、TCP FIN/RST、超时、CTR 跳号、错误 Profile 和资源清理；固定解码器的可选 Tail 语义须独立验证，不将人为生成的边界视为真实 TCP 消息边界。
- **诊断与副作用**：候选失败原因区分，试连次数与超时有界；用户取消或失败后连接被清理；CLI 兼容性按批准策略覆盖。
- **真实互操作**：按 §4.3 分别运行 `thirdparty/XCPlite` 和 `thirdparty/XCPliteV1.2` 的独立进程门禁；另用独立 V1.5 实现或设备验证有区分度行为。若无独立 V1.5 对端，标记“未验证”，不能由 mock 代替。
- **环境和构建**：遵循项目要求，Release 全量构建前先 clean；相关自动化测试和测试结果记录于 `code-plan`。Windows/Linux/macOS 分别报告实际执行情况，不以一个平台外推其他平台。

### 4.3 两套 XCPlite 真实互操作门禁

目标是验证应用层从 A2L 到连接决策、再到真实 TCP 通信的链路，不能只测试固定 Profile 的底层 `XcpMaster` 通信并宣称 `xcp_master` 的自动决策已覆盖。具体 CLI/TUI 入口、无交互测试方式及测试夹具复用方案在 M1 设计评审时确定。

| 对端 | 现有可复用基础 | 新增验收重点 | 证据边界 |
|---|---|---|---|
| `thirdparty/XCPliteV1.2` | `tests/xcp_v12_interop_test.cpp`、`tests/xcp_v12_slave_process.cpp` 和 `examples/xcp_slave_demo_v12`，已有 TCP/UDP 测量与标定用例 | 使用对应从站生成的 TCP A2L；检查端点、版本、alignment 声明状态及来源；经应用决策入口建立 TCP 会话；复验测量读取、标定写入回读与断连 | 只证明该 V1.2 实现及实际覆盖的配置，不能泛化至全部 TL 1.4 设备 |
| `thirdparty/XCPlite` | `tests/xcplite_tcp_interop_test.cpp`、`tests/xcplite_slave_fixture.cpp` 和 `tests/xcp_test_slave`；后者由 `tests/xcp_test_slave/CMakeLists.txt` 链接 `xcplite::xcplite` | 使用该从站对应的 A2L，验证同样的事实提取、候选及来源、TCP 连接、测量读取、标定写入回读与断连；检查现有互操作不回退 | 只证明当前仓库该版本及实际覆盖的配置；不能单凭版本名称或测试通过认定其为 V1.5 独立一致性对端 |

共同测试要求：

1. 两套协议栈分别以独立从站进程运行，不在同一进程混链同名协议符号；复用现有 C++ 进程夹具，不用 Python 启动从站，也不修改第三方源码。
2. 记录 A2L 的实际声明而非假设一定包含 alignment；声明缺失时按批准策略报告缺失或歧义，不能用默认值冒充显式声明。验证真实 A2L 与从站端点匹配。
3. 分别断言应用层选择的候选、证据来源、运行结果及歧义状态；`CONNECT` 成功但无法排除其他候选时不得声称唯一识别。真实环境只覆盖实际出现的声明和线路行为，其他组合由可控测试补足。
4. 覆盖端口不可达、连接或验证失败后的超时和进程清理；用确定性测试对手端覆盖无法稳定由真实从站制造的分片、任意 FILL、截断与冲突，不伪造其为真实对端行为。
5. 两套门禁各自报告测试对端、传输、A2L、配置、执行平台和结果，缺少某套构建条件或设备时明确标记未验证，不用另一套通过结果代替。
6. `tests/xcplite_tcp_interop_test.cpp` 文件头目前将 `xcp_test_slave` 误称由 `XCPliteV1.2` 构建；实际归属以构建依赖为准，实施前再核验并在获批的代码修改中修正文档注释。

### 4.4 多 alignment 专项测试矩阵

alignment 以 bit 表示（8/16/32 分别对应 1/2/4 字节）。分别验证 A2L 事实、决策、固定配置下的线路行为和真实对端；不把 A2L 声明等同于对端实际行为，也不把单次 CONNECT 成功当作识别结果。

| 类别 | 8 bit | 16 bit | 32 bit | 核心断言 |
|---|---|---|---|---|
| A2L 与配置 | 显式 8、缺失、非法和重复声明 | 显式 16、缺失、非法和重复声明 | 显式 32、缺失、非法和重复声明 | 值与来源正确；缺失、无效、冲突不能冒充有效声明；CLI 与 A2L 冲突按获批策略处理 |
| V15 固定配置 | 无需 LEN 外对齐填充 | 不同 LEN 覆盖需 0/1 字节填充 | 不同 LEN 覆盖需 0/1/2/3 字节填充 | 独立构造预期字节核对收发及后继消息；FILL 内容任意；区分规范允许的单消息可选 Tail 与实现能力 |
| 不可区分样本 | V14/8 与 V15/8 共同字节序列 | 报文长度恰好不要求填充 | 报文长度恰好不要求填充 | 多候选可解释观察时报告相容但未唯一确认，不按候选顺序或 CONNECT 成功宣称确定 |
| 边界和错误 | 分片、合包、FIN/RST | Tail 分片、合包、FIN/RST | Tail 分片、合包、FIN/RST | 覆盖任意 FILL、截断、错误配置、CTR 和清理；不把 recv、超时或 FILL 值当帧边界 |
| 两套 XCPlite 真实进程 | 对端实际支持或声明的配置 | 同左 | 同左 | 每套记录 A2L 声明、构建配置、线路观察和结果；只运行已确认受支持的组合 |

- V14 兼容 Profile 不消费 LEN 外 Tail：即使其对端 A2L 声明 16/32，也不得将该值自动解释为 V15 LEN 外填充；用 V1.2 对端和确定性样本分别验证并注明证据范围。
- 每个连接固定 Profile/alignment；候选重试采用独立连接，不通过配置切换或等待超时猜测 Tail。发送与接收方向分别测试，覆盖不同连续消息长度组合。
- 不假定两套 XCPlite 均能配置并实际支持全部 8/16/32 组合；实施前核查配置、A2L 与实际线路。无法构造的组合标记未验证，不改受限第三方、不篡改 A2L 冒充真实设备；自有可控对手端的测试不能称为第三方互操作。
- 冲突和非法 A2L 等由受控样本构造；真实对端使用与实际配置一致的 A2L。独立 V1.5 对端可用时针对其支持的 alignment 分别记录；不可用时明确未验证。
- 第二阶段复跑本矩阵，比较提取前后的候选、结果分类、来源及线路行为；纯决策测试不能替代线路和真实进程测试。

第一阶段完成条件：以上约定范围内测试通过、无法唯一识别的情形正确保留歧义、结果与限制已记录；未验证的独立对端和平台明确列出。

## 5. 第二阶段：提炼可复用组件

### 5.1 提取前提

第一阶段完成且语义经使用验证；先梳理实际重复使用者、所需事实和生命周期，再提交可复用模块设计评审。不得为提取而改变第一阶段已验证的决策结果。

### 5.2 建议边界

- **输入**：与 UI、A2L 文件解析器解耦的结构化连接事实、证据来源、候选及明确策略；不得以具体工具的全局状态为依赖。
- **核心决策**：候选筛选、证据融合、冲突/歧义分类和结构化解释；不直接读取 A2L 文件、不要求 glog 或 TUI。
- **连接执行适配**：如需执行试连，通过明确注入的执行接口提供结果；资源生命周期、超时、取消和副作用由设计单独定义。纯决策与网络 I/O 尽量分离。
- **输出**：结构化结果、候选、证据及失败原因；应用层负责展示和用户确认。实际类型、命名、ABI/API、同步或异步模型均待专项评审。
- **使用者**：`xcp_master` 首先迁移；再用最小独立调用方验证无需 CLI、TUI 或 A2L 解析器也能使用。

### 5.3 第二阶段测试与验收

- 将第一阶段决策矩阵作为行为契约，迁移前后用同一输入验证候选、结论和证据一致。
- 单测注入相容、冲突、超时、取消、异常和多候选结果；验证无全局状态泄漏、生命周期与清理。
- 检查公共接口头文件依赖、平台构建、版本/ABI 兼容及独立调用者编译；如新增公共接口，按项目要求补齐接口测试和中文 Doxygen 注释。
- 复跑 §4.3 的两套 XCPlite 真实 TCP 互操作门禁，比较提取前后候选、证据、歧义和连接行为；根据实际条件复跑独立 V1.5 互操作，并更新使用说明与实施记录。

第二阶段完成条件：`xcp_master` 使用复用组件、独立调用者可用、行为回归通过、依赖边界与限制清晰记录。

## 6. 里程碑与评审门禁

| 顺序 | 交付 | 门禁 |
|---|---|---|
| M0 | 基线、A2L 有效性缺口及用户选项细化 | 用户确认冲突、歧义和 auto 兼容策略 |

## 7. 确认记录及剩余问题

已确认：优先复用现有 `XcpMaster::Connect()` 内已有命令，不新增只读探测；多次候选试连仍可能影响从站会话。严格 auto 在连接前已知存在不可区分候选时直接报告歧义，不连接设备。A2L alignment 使用有限范围严格校验：无真实 INCLUDE、唯一模块及连接块且归属可判定的输入，扫描和 SDK 读取同一受控临时快照，核对 alignment 字面量、重复声明和所选端点；否则标记不可信并要求用户显式配置。快照须唯一命名、受限权限及 RAII 清理，不承诺抵御同权限恶意进程篡改；不得修改原文件或受限第三方。自动化测试调用工具内部共享决策代码并启动独立 C++ 从站进程，不声称覆盖完整交互式 TUI。以下历史问题保留供追溯，其中 1–4 的策略以本段及 §3.2 的确认记录为准；具体实现细节、5–6 仍需评审。

1. **现有 `--tcp-profile auto`**：建议改变其结果表述，默认保留歧义并要求显式选择；若需要兼容旧脚本，是否允许保留一个明确标记风险的旧式首成功模式？
2. **CLI 与 A2L 冲突**：建议默认拒绝并报告；是否允许用户通过显式选项确认覆盖？
3. **A2L 非法 alignment**：现有下游声明位不能证明字面量合法。需先调查不修改受限第三方的可行路径；若确需修改 `thirdparty/a2llib`，必须先获得用户对该第三方修改的明确授权。
4. **主动验证范围**：建议仅在用户同意后采用有界、低风险连接验证；额外 XCP 命令、次数、超时及 ECU 运行安全边界需逐项确认。
5. **可选 Tail 和 FIN 疑点**：建议单独建立复现测试和影响分析，再决定是否纳入修复，不以本计划自动授权。
6. **独立 V1.5 设备和跨平台环境**：待确认是否具备；缺少时作为未验证项，不阻止准确汇报已完成的子范围。
