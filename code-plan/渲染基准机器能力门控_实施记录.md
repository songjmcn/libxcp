# 渲染基准机器能力门控 实施记录

## 1. 背景

`XcpMasterRenderBenchTest.RendersFrameWithFieldSizeCandidateList` 在 Windows 本机全量 ctest 中稳定失败，其余 1047 个用例全部通过（`cmake-build-vs`，VS 2022 x64 Release，与 `.github/workflows/msbuild.yml` 同参数）。

实测数据（连续 4 次，219 s 内交叉复跑）：

| 项目 | 数值 |
| --- | --- |
| 单帧渲染 198 556 行 | 715.1 / 780.2 / 798.4 / 858.5 ms |
| 参考值 `kFrameRenderReferenceMs` | 170.0 ms |
| 参考预算（参考值 × 3） | 510.0 ms |
| 绝对上限 `kFrameRenderHardLimitMs` | 1500.0 ms |
| 推导出的每行成本 | 参考 0.856 µs/行，本机 4.6~5.1 µs/行 |

结论：该失败**不是**平台缺陷，也不是本次 Windows ctest 修复引入的回归——它与 TCP 传输层、日志层无调用关系，且同一构建里同文件的另外 4 个用例（虚拟菜单 0.07 ms、线性增长 3.73 倍、大 A2L 检索 211 ms）全部通过。真实原因是本机渲染每行成本约为参考机的 5 倍，绝对毫秒预算在这种机器上没有判别力。

CI 侧本来就通过：`msbuild.yml` 的 ctest 步骤带 `-E "XcpMasterRenderBenchTest|a2l_ui_perf_gen|a2l_perf_gen|ParseLargeFileUnderBudget"`，该套件在 CI 中被排除。故本次改动只为让**本地全量**恢复全绿，同时不静默放宽阈值。

## 2. 设计决定（已获用户批准）

用户明确选择"机器能力不匹配时跳过"的**显式门控**，而不是重新标定预算或悄悄放宽阈值。

### 2.1 门控信号：同路径小规模标定

新增 `MeasureMachineCapabilityFactor()`：用**同一条渲染路径**测量 1/16 规模（`kCapabilityProbeRows = 12 409` 行）的每行成本，除以参考机每行成本 `kFrameRenderReferenceUsPerRow`，得到能力系数。

不采用独立纯 CPU 标定负载的原因：本基准瓶颈在内存与字符串分配（FTXUI 的 `Menu::OnRender()` 对每个条目构造一次 `Element`），通用 CPU 系数（本机约 1.5 倍）与实际耗时（约 5 倍）不呈比例，会把慢机误判为代码劣化。

### 2.2 判定顺序

1. `frame_ms >= kFrameRenderHardLimitMs` → **失败**（任何机器都不豁免，量级劣化不会被放过）；
2. `frame_ms < reference_limit` → **通过**（行为与门控引入前完全一致）；
3. 介于两者之间：能力系数 > `kMachineCapabilityTolerance`(2.0) → `GTEST_SKIP` 并打印完整证据；否则 → **失败**（同档机器上的真实劣化照常拦截）。

### 2.3 已知代价（明示，不隐藏）

系数基于"同代码路径"标定，因此**代码整体劣化同样会抬高系数**，在慢机上可能被归类为"机器不匹配"而跳过。兜底只剩绝对上限 1500 ms。跳过消息中明确写出"若怀疑是代码劣化，请在参考机复核该基准"，把复核责任显式交给参考机。

## 3. 改动清单

仅一个文件：`tests/xcp_master_render_bench_test.cpp`

- 新增常量（中文 doxygen 注释）：
  - `kFrameRenderReferenceUsPerRow`：由 `kFrameRenderReferenceMs / kFieldCandidateCount` 推导（≈0.856 µs/行），不引入新魔法数；
  - `kMachineCapabilityTolerance = 2.0`；
  - `kCapabilityProbeRows = kFieldCandidateCount / 16U`（12 409 行，标定开销约 0.3 s）。
- 新增 `MeasureMachineCapabilityFactor()`，注释说明同路径标定的取舍。
- `RendersFrameWithFieldSizeCandidateList` 改为三段式判定（见 2.2），`[PERF]` 行补充每行成本与能力系数。
- 文件头注释补充门控语义。
- 同文件其他预算（检索 90 ms / 过滤 60 ms / 虚拟菜单 0.5 ms）**不改**：本机余量充足，避免超范围改动。

## 4. 验证结果

### 4.1 用例级（`cmake-build-vs\tests\Release\XcpMasterRenderBenchTest.exe`）

```
[PERF] 渲染 198556 行单帧 = 715.1 ms（预算 参考=510 ms 硬上限=1500 ms）；本机每行 4.57 µs，参考每行 0.86 µs，能力系数=5.34
...Skipped
本机算力与参考机不匹配，绝对毫秒预算无判别力：实测单帧 715.1 ms，参考预算 510 ms，硬上限 1500 ms（已通过）；
本机每行 4.57 µs，参考每行 0.86 µs，能力系数 5.34 > 容忍倍数 2.0。若怀疑是代码劣化，请在参考机复核该基准。

[  SKIPPED ] XcpMasterRenderBenchTest.RendersFrameWithFieldSizeCandidateList (3128 ms)
```

同文件其余 4 个用例：`4 tests passed`（虚拟菜单 0.07 ms / 线性增长 3.73 倍 / 大 A2L 检索 211.3 ms），整套 5 个用例 12.9 s，`exit=0`。

### 4.2 编译

`cmake --build cmake-build-vs --config Release --target XcpMasterRenderBenchTest` → `build_exit=0`，无 error、无新增警告。

## 5. 环境备注（不影响仓库）

本机构建时需先清空 8 个代理环境变量（`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` 及其小写），否则 MSBuild 报 `error MSB6001: “CL.exe”的命令行开关无效。System.ArgumentException: 已添加项。字典中的关键字:“HTTP_PROXY”所添加的关键字:“http_proxy”`（DSH 注入的大小写重复键触发了 `ProcessStartInfo.EnvironmentVariables` 的字典冲突）。CI runner 无此问题。
