## 2. 规范核对要点

- `GET_DAQ_CLOCK`（规范 §7.5.4.10）：CTO 仅一字节 `[0xDC]`。legacy 正响应为 `[0xFF][reserved][TRIGGER_INFO][PAYLOAD_FMT][DWORD]`，其中 DWORD 的具体格式由 `GET_DAQ_RESOLUTION_INFO` 的时间戳位宽决定。extended 正响应在时钟值之后可追加 grandmaster 时钟、ECU 时钟与 `SYNC_STATE`；只要存在可同步/锁频的时钟，`SYNC_STATE` 必须存在。`MAX_CTO = 8` 时即使启用了高级特性也必须退回 legacy。**master 不得使用 `TRIGGER_INFO` 中的 `TRIGGER_INITIATOR`**——它是 Slave 自述的触发来源，不是配置手段。
- `GET_DAQ_CLOCK` 不能按需读取相关时钟时，Slave 必须回 `ERR_RESOURCE_TEMPORARY_NOT_ACCESSIBLE` 而不是给个正响应。因此本实现把该错误当作"此刻读不到"正常上抛，**不吞成 `nullopt`**（`nullopt` 只表示 `ERR_CMD_UNKNOWN`）。
- `TIME_CORRELATION_PROPERTIES`（规范 §7.5.6.1）：`SET_PROPERTIES` 的 `RESPONSE_FMT` 取值 0 的含义是"**不改变**"，协议里**没有**"降级回 legacy"的取值；`TIME_SYNC_BRIDGE` 同理。没有桥接特性时 Slave 会静默忽略 enable/disable 请求，所以任何设置都必须回读确认。
- Clock info 变更后，Slave 在测量启动时必须回 `ERR_TIMECORR_STATE_CHANGE`，master 需重新上传 clocks 信息，否则不得开始测量。
- **响应长度陷阱**：规范表格的字节数统计**包含 0xFF 正响应码**。`TIME_CORRELATION_PROPERTIES` 表 212 共 8 字节，剥掉 PID 后是 **7**；`DTO_CTR_PROPERTIES` 表 164 共 5 字节，剥掉 PID 后是 **4**。本批与 B2 各踩了一次，作为通用教训记录于此。

## 4. 设计决策

1. **"改不回去"的 API 直接拒绝**。`SetClockResponseFormat(ResponseFormatMode::Legacy)` 抛 `InvalidArgument` 而不是"尽力而为地写 0"。规范中 `RESPONSE_FMT = 0` 是"不改变"，写 0 只会静默无操作却让调用方以为降级成功。这是把协议事实编码进类型/参数校验，而不是文档里提醒一句。
2. **设置必须回读**。`TIME_SYNC_BRIDGE` 在无桥接的 Slave 上被静默忽略是规范允许行为，故仅"发送成功"不构成已完成；`SetClockResponseFormat` 返回的是回读后的快照，不一致即抛 `UnsupportedFeature`。
3. **三种 `EV_TIME_SYNC` 布局用枚举显式表态**，不做"看长度猜布局"。`MAX_CTO = 8` 的 extended 与 `MAX_CTO != 8` 的 extended 第二字节一个是 counter、一个是 `PAYLOAD_FMT`，长度也可能撞在一起，猜错会静默解出错值。
4. **`ERR_RESOURCE_TEMPORARY_NOT_ACCESSIBLE` 与 `ERR_CMD_UNKNOWN` 严格区分**。前者是"现在读不到"（可重试、应上抛），后者是"Slave 没这命令"（降级）。把前者吞成 `nullopt` 会让调用方误以为设备不支持时间关联。
5. **Clock Info 只回原始字节**。本批不解析 18/16/8 字节结构体内部字段：`Native timestamp size` 合法性、`Stratum` 等语义校验属于后续独立工作，先保证"按协议取回、不越界、不猜测"。
6. **`GET_CLK_INFO` 会打断 MTA 上下文**，因此执行器主动失效 `m_last_mta_`，避免恢复逻辑按旧地址重放。

### 5.2 测试暴露的缺陷

1. **`kTimeCorrelationResMinSize` 写成 8（应为 7）**：12 个用例连锁失败，报 `TIME_CORRELATION_PROPERTIES 响应长度不足（RES 数据 7 字节，期望 >= 8）`。根因是把规范表 212 的字节数（含 `0xFF`）当成了 RES 数据长度。修正解析器常量并同步执行器错误文案。
2. **测试装置默认行为假设错误**：`ClockSlave` 的 switch 对 `TIME_CORRELATION_PROPERTIES` 始终回合法体，而用例以为默认回 `ERR_CMD_UNKNOWN`，导致"不支持时返 `nullopt`"的断言失败。改为用例内显式 `FailWith(..., ErrorCode::CmdUnknown)`。
3. **`EcuClockObservabilityOf(0x69)` 期望值错**：`0x69 >> 4 = 6`，`6 & 3 = 2` 即 `EventOnly`，不是 `RandomReadable`。是测试期望写错，实现正确。
4. **帧序号错位**：`SetClockResponseFormat` 内部会先自动查询一次，用例里再手工查询一次导致 `frame[1]` 取到的是内部查询帧（`0x00`）。去掉手工查询后帧序为 0=内部查询、1=真正下发。
5. **`EXPECT_THROW` 触发 C4834**：宏内丢弃 `[[nodiscard]]` 返回值，改为 `EXPECT_THROW(static_cast<void>(call), ...)`；`(void)` 写法不足以消除该警告。

## 6. 边界与遗留

1. **未实现精确对时**：`ReadDaqClock` 返回的是 Slave 侧时钟采样值及其格式，**不**包含 Host 本地收发时刻、往返延迟估计与时钟域换算。按计划本批只做"基础时间关联"，不得对外声称"精准同步"。
2. **Clock Info 数据块不解析**：只回原始字节。`Native timestamp size` 只允许 4/8、`Stratum = 255` 表示未知、`Epoch` 语义等校验尚未实现。
3. **`AG > Byte` 时拒绝上传 Clock Info**：18/16/8 字节块不是 `WORD`/`DWORD` 粒度的整数倍，按元素读取会越界。当前策略是抛 `UnsupportedFeature`，不做字节级 Read。
4. **`SetClockResponseFormat` 无法降级**：协议没有对应取值，本库直接拒绝。若某 Slave 真的支持私有降级手段，需要独立机制，不在 XCP 标准范围内。
5. **`ERR_TIMECORR_STATE_CHANGE` 只上抛，未自动恢复**：测量启动收到该错误时，调用方需重新 `QueryClockCorrelation()` 并重新上传 Clock Info，本批不做自动重编排。
6. **`EV_TIME_SYNC` 只提供解析入口**：尚未接入事件分发链路（`IEventListener`）做主动时基同步消费。
7. **时间戳回绕与时钟域仍分离**：`DaqTimestampConverter` 只做位宽回绕延展；`DaqTimestampRelation` 仅作为元数据对外暴露，尚未把 ECU 时钟域与 XCP slave 时钟域换算串起来。

## 7. 自审

- 是否凭记忆编造 API？—— 所有签名均从当前头文件读取后写入，实施记录中的行号在本批结束时用 `grep -n` 复核。
- 是否把"命令能编码"当成"功能完成"？—— 本批验收覆盖 Codec/Parser/Executor/Master 四层的正向与错误路径，并区分了 `ERR_CMD_UNKNOWN`（降级）与 `ERR_RESOURCE_TEMPORARY_NOT_ACCESSIBLE`（上抛）。
- 是否夸大能力？—— §1 与 §6 明确排除精确对时、Multicast、桥接与多 Slave 策略；文档中未使用"精准同步"表述。
- 测试是否独立于实现自证？—— 用例直接断言线格式字节、解析字段与主站可见状态变化，并对"静默忽略"这类 Slave 行为构造了失败场景。
- 遗留项是否具体可执行？—— §6 七条均指到具体函数或协议条目，可直接转成后续任务。
