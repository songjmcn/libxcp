# poll / DAQ 性能统计实施计划（滑动窗口 + 分阶段耗时 + 可配置）

> 状态：计划已定稿，**尚未写代码**。
> 依据：用户 m05142（要滑动窗口 + 分阶段耗时）、m05190（窗口默认 5 s 但要配置 API；DAQ 每帧都测但要配置 API；slowest 要给更多信息）。
> 关联任务：`_todo/tasks/perf-stats-plan.md`、`perf-window-core`、`perf-poll-stages`、`perf-daq-stages`、`perf-tool-metrics`、`perf-calibration-integration`。

## 1. 目标与范围

给 libxcp 的 poll 与 DAQ 两条采集路径加可开关的性能统计：

1. 按**墙钟滑动窗口**聚合，一个窗口只输出一块日志，日志频率与采样频率解耦；
2. 统计**每个阶段**的耗时（均值 / p95 / 最大 / 占比），阶段之和可加和成总耗时，用于定位热点；
3. 统计**最慢的变量**（不止名字，见 §7）；
4. 全部参数都能在运行期通过 API 改（用户要求，便于上线后按现场调整），环境变量作为一次性入口。

不做的事：

- 不改传输层、协议层、A2L 层；
- 不引入新第三方依赖（聚合器 header-only，只用标准库）；
- 不修改 `PollStatistics` / `MeasurementStatistics` 的既有字段（它们是公开 ABI 面，只追加新接口）。

## 2. 三个设计不变量

| # | 不变量 | 理由 |
| --- | --- | --- |
| I1 | 日志按墙钟窗口，不按 tick 数 | tick 周期会变（多 event 后每个 event 周期不同），按 tick 计会让日志忽快忽慢 |
| I2 | 阶段耗时必须可加和 | `sum(阶段) ≈ total`，否则"占比"是假的，会把噪声当热点 |
| I3 | 埋点不改变被观测对象语义 | 不加锁、不在实时线程里格式化字符串、窗口聚合不引入新热点 |

## 3. 配置 API（本次新增，用户明确要求）

### 3.1 配置结构

```cpp
namespace calmcar::xcp {

/// @brief 性能统计的运行期配置。
/// @details 整体替换、整体生效：调用 SetPerfConfig() 传一份新配置，统计线程在
///          下一个窗口边界读取它；不提供逐字段 setter，避免半更新状态。
struct PerfConfig {
    /// @brief 总开关；false 时不采样、不聚合、不写日志。
    bool enabled{true};

    /// @brief 日志窗口长度（墙钟）。默认 5 s。
    /// @note 窗口过短会让 p95 失去统计意义（样本 < 20），下限建议 500 ms。
    std::chrono::milliseconds window{5000};

    /// @brief 采样率：每 N 次事件测一次。
    /// @details poll 侧 N 通常为 1；DAQ 在 1 kHz 下可用 4~16 降低开销。
    ///          N == 0 等价于 1。计数按事件累加，窗口边界不重置计数。
    std::uint32_t sample_every{1};

    /// @brief slowest 记录的槽数（阶段×变量）。0 表示不统计慢点。
    std::size_t slowest_capacity{5};

    /// @brief 是否把窗口摘要写进日志；false 时只保留 PerfSnapshot() 供程序内读取。
    bool log_to_logger{true};

    /// @brief 是否输出各阶段明细行；false 时只输出 total 一行（日志更短）。
    bool verbose_stages{true};
};

}  // namespace calmcar::xcp
```

### 3.2 来源与优先级

配置只有一个来源链，**后者覆盖前者**：

1. 编译期缺省 `PerfConfig{}`（5 s、sample_every=1、slowest=5、开启）；
2. 环境变量（进程启动时读一次）——`PerfConfigFromEnvironment()`；
3. 运行期 `SetPerfConfig()`（最高优先级，随时可改）。

环境变量：

| 变量 | 类型 | 含义 |
| --- | --- | --- |
| `LIBXCP_PERF_ENABLED` | `0/1` | 总开关 |
| `LIBXCP_PERF_WINDOW_MS` | 毫秒 | 窗口长度，`0` 视为关闭 |
| `LIBXCP_PERF_SAMPLE_EVERY` | 正整数 | 采样率 |
| `LIBXCP_PERF_SLOWEST` | 非负整数 | slowest 槽数 |
| `LIBXCP_PERF_VERBOSE_STAGES` | `0/1` | 阶段明细行 |

解析失败的项**保留缺省值并记一条 WARNING**，绝不因为环境变量写错就关闭统计或抛异常。

```cpp
/// @brief 从环境变量构造配置，非法值回落到缺省并记告警。
[[nodiscard]] PerfConfig PerfConfigFromEnvironment();
```

### 3.3 两个 Session 的运行期 API

```cpp
class PollSession {
public:
    /// @brief 替换性能统计配置，在下一个窗口边界生效。
    /// @note 线程安全；可从任意线程调用。
    void SetPerfConfig(const PerfConfig& config);

    /// @brief 读取当前生效配置（拷贝）。
    [[nodiscard]] PerfConfig PerfConfigValue() const;

    /// @brief 取一份窗口快照并清零累计（不依赖日志）。
    [[nodiscard]] PollPerfSnapshot PerfSnapshot();
};
```

`MeasurementSession` 提供同名同义的三项。**构造函数**追加末位默认参数，不破坏既有调用：

```cpp
explicit PollSession(XcpMaster& master,
                     const IMeasurementDatabase& database,
                     PerfConfig perf_config = PerfConfigFromEnvironment());
```

### 3.4 生效时机与线程安全

- 配置存 `std::mutex config_mutex_` + `PerfConfig config_`，只在**窗口边界**读一次（每 5 s 一次锁，代价可忽略）；`Record()` 路径完全不碰锁。
- `enabled` 从 `true → false`：立即停止采样，且**丢弃当前未完成的窗口**（不写半截日志）。
- `enabled` 从 `false → true`：从下一个事件开始采样，第一个窗口从第一个采样事件起算。
- 窗口长度变更：不打断当前窗口，下一个窗口生效。
- 采样率变更：立即生效（用事件序号取模，序号持续累加）。

## 4. 聚合器（`include/libxcp/detail/perf_window.hpp`，header-only）

```cpp
enum class PerfStage : std::uint8_t {
    ScheduleGap, GroupRead, SingleRead, Convert, Assemble, Callback, TickTotal,   // poll
    RxEnqueue, QueueWait, EnvelopeDecode, PayloadDecode, E2e,                     // DAQ
    Count
};

/// @brief 单阶段的窗口累计。
struct StageWindow {
    std::uint64_t count{0};
    double sum_ms{0.0};
    double max_ms{0.0};
    std::array<std::uint32_t, 16> buckets{};  ///< 0.1/0.25/0.5/1/2/5/10/20/50/100/…
};

class WindowAggregator {
public:
    void Record(PerfStage stage, double duration_ms, std::string_view symbol = {}) noexcept;
    [[nodiscard]] bool Due(std::chrono::steady_clock::time_point now) const noexcept;
    [[nodiscard]] PerfWindowSnapshot TakeSnapshot(std::chrono::steady_clock::time_point now);
    void Reset() noexcept;
};
```

- `Record` 标 `noexcept`，无锁、无堆分配（`symbol` 只拷进固定槽）。
- p50/p95/p99 由 16 个桶插值近似；桶边界写死，改边界会破坏跨版本可比性。
- 时钟可注入：`using NowFn = std::function<std::chrono::steady_clock::time_point()>;` 构造参数，默认 `steady_clock::now`，单测用假时钟做确定性断言。
- 内存：`StageWindow` ≈ 112 B × 13 阶段 ≈ 1.5 KB/会话，可忽略。

## 5. poll 阶段划分

| 阶段 | 起止点（`src/poll/poll_session.cpp`） |
| --- | --- |
| `ScheduleGap` | 计划时刻 `state.next` → `sample.steady_time`（:400） |
| `GroupRead` | `ReadMemoryBytes(group)`（:416-418），累加所有合并组 |
| `SingleRead` | `ReadSingle()` 的 `ReadMemoryBytes`（:386-387），只有合并组失败回退时发生 |
| `Convert` | `ConvertInto`（:324-372），标量 `ToPhysical` / 数组逐元素 `ToPhysicalElement` |
| `Assemble` | 结果装配、`std::move`、`results` 构造 |
| `Callback` | `m_callback_(sample)`（:443） |
| `TickTotal` | `steady_time` → `steady_time_end`（:400 / :439） |

配套计数：`variables`、`groups`、`overruns`、`read_errors`、`callback_errors`；合并率 = `1 - groups/variables`（评估地址合并是否生效的唯一数字）。

配套**字节量**计数（用户要求：输出合并读取的长度）：`group_bytes_total`（窗口内所有合并组读取的总字节）、`group_bytes_max`（单组最大字节）、`group_slices_total`（被合并进组的变量总数）。由它们派生：

- `bytes/tick = group_bytes_total / ticks`：每次 tick 平均从 ECU 读回多少字节，是带宽占用的直接度量；
- `group_mean = group_bytes_total / groups`：一次合并读平均多大；
- `vars/group = group_slices_total / groups`：一次合并读平均覆盖几个变量。

合并率只说明"合并发生了几次"，字节量才说明"每次合并值多大"——同样 `merged=71%`，组均值 4 B 和 420 B 在 XCP 报文层面是完全不同的代价。

### 5.1 合并读取的判据：与数据类型无关

`ResolveEvent()` 的归并只比较三个条件（`src/poll/poll_session.cpp:145-165`）：同一 `extension`、上一组末地址 `==` 本变量地址、地址不越 `0xFFFFFFFF`。**数据类型只通过 `byte_count = element_size_bytes × element_count` 影响组向前推进多少字节，不参与"是否合并"的判断**：

| 布局 | 是否合并 | 依据 |
| --- | --- | --- |
| `U32 a` @0x1000、`U32 b` @0x1004 | 合并 | 0x1000 + 4 == 0x1004 |
| `U8 a` @0x1000、`U32 b` @0x1001 | 合并 | 0x1000 + 1 == 0x1001（类型不同照样合） |
| `U32 a` @0x1000、`U32 b` @0x1008 | 不合并 | 0x1000 + 4 = 0x1004 ≠ 0x1008（中间 4 B 空隙） |
| `float[32] a` @0x1000、`U8 b` @0x1080 | 合并 | 数组整段 128 B，0x1000 + 128 == 0x1080 |

因此能否合并取决于 A2L 里变量的**地址排布**，而不是类型；`tests/poll_capacity_calibration.cpp` 用 `kProbeStride = 4` 取两两不相邻的地址，正是为了量"合并完全失效"的最坏情况。

推论：`GroupRead` 的耗时是**整组共担**的，无法归属到单个变量，所以日志必须同时给出组内变量数与字节数，否则"3.4 ms 的 group_read"会被误读成某一个变量很慢。

## 6. DAQ 阶段划分

| 阶段 | 说明（`src/measurement/measurement_session.cpp`） |
| --- | --- |
| `RxEnqueue` | `OnDto` 全程（:490-506，入队 + 锁竞争），变大即丢帧前兆 |
| `QueueWait` | 入队 → worker 取帧（:512 起） |
| `EnvelopeDecode` | `DtoEnvelopeDecoder` 解信封 |
| `PayloadDecode` | 逐切片解码 + `ToPhysical` |
| `Callback` | 用户回调 |
| `E2e` | RX 入队时刻 → 回调开始（端到端延迟） |

`E2e` 需要队列元素从 `Bytes`（:501）改为 `{Bytes, 到达时刻}`——唯一触及核心数据结构处，纯追加字段。`sample_every` 按帧计数，未采样帧的 `E2e` 不统计，避免"只测一半却算成全体"。

## 7. slowest：记录更多信息（用户要求 3）

不只是变量名，而是**阶段×变量**的窗口累计：

```cpp
/// @brief 一个慢点：同一 (阶段, 变量) 在窗口内的累计表现。
struct SlowSpot {
    std::string symbol;            ///< 变量规范名（module::name）
    PerfStage stage{PerfStage::Convert};  ///< 该慢点所属阶段
    std::uint64_t count{0};        ///< 窗口内采样次数
    double sum_ms{0.0};            ///< 窗口累计耗时（排序依据）
    double max_ms{0.0};            ///< 单次最大
    std::uint32_t group_size{1};   ///< GroupRead 专用：该组含几个变量（≥2 才算合并）
    std::uint32_t group_bytes{0};  ///< GroupRead 专用：该组的读取长度（字节）
};
```

排序与输出规则：

- 容量 `slowest_capacity`（默认 5）个槽，按 `sum_ms` 降序；满了之后新的候选若 `sum_ms` 大于当前最小槽才插入（O(k) 线性替换，k≤8）。
- 同一变量出现在多个阶段时**各占一槽**，日志里带 `[阶段]` 前缀，避免把 `group_read` 与 `convert` 混成一个数。
- 另给一行**按变量聚合**（跨阶段求和）的 `hottest`，回答"哪个变量最贵"。
- `GroupRead` 的耗时整组共担，记在组内**首变量**名下，并用 `group_size` / `group_bytes` 标注"组 N 变量 / M B"——不这样标，读者会把整组代价误当成单个变量的代价。

日志形态：

```
[perf][poll event=BMS_10ms] window=5.000s ticks=250 vars=42 groups=12 merged=71.4%
                             bytes/tick=1.8KiB group_mean=184B group_max=420B
                             overrun=0 (0.00%) read_errors=0
  total      n=250 mean=1.82ms p95=2.40ms max=6.10ms
  group_read n=12/250 mean=0.90ms p95=1.20ms max=3.40ms (49.5%)
             vars/group=3.5 max=7  bytes/group=184B max=420B
  convert    n=250 mean=0.61ms p95=0.85ms max=2.10ms (33.5%)
  callback   n=250 mean=0.21ms p95=0.40ms max=1.80ms (11.5%)
  sched_gap  n=250 mean=0.08ms p95=0.30ms max=2.90ms
  slowest: EngineSpeed[convert]    n=250 sum=105.0ms mean=0.420ms max=0.90ms (12.1%)
           MAF[convert]            n=250 sum=77.5ms  mean=0.310ms max=1.20ms (8.9%)
           Lambda[group_read]      n=12  sum=41.0ms  mean=3.420ms max=4.10ms (4.7%) 组4变量/56B
  hottest: EngineSpeed total=112.4ms (n=250, 2 stages)
```

- `n=a/b` 表示"参与该阶段的次数 / 窗口 tick 数"，能一眼看出该阶段是否每次都发生（如 `group_read` 只发生在有合并组时）。
- `(12.1%)` 是该慢点 `sum_ms` 占窗口 `TickTotal` 累计的比例。
- `hottest` 只列前 3 个变量，`2 stages` 说明它跨了几个阶段（提示"是不是多个阶段都慢"）。

- 第 2、3 行是**字节量**摘要：`bytes/tick` 直接乘周期即得所需带宽（如 1.8 KiB / 20 ms ≈ 92 KiB/s）；`group_mean` / `group_max` 说明一次合并读的规模。
- `group_read` 下方的 `vars/group` 与 `bytes/group` 给的是组内形态：若 `merged` 很高但 `bytes/group` 只有几字节，说明合并只在细小变量上生效，收益有限。

## 8. 日志与控制

- 走 `LIBXCP_LOG_INFO`（`include/libxcp/log.hpp:40-48`），前缀 `[perf]`，一个窗口**一块**（不是每阶段一行）。
- 输出时机在窗口边界，位于统计线程内但**不在关键读取路径**上；格式化失败不得影响采集。
- `log_to_logger = false` 时只保留 `PerfSnapshot()`，供程序自取（嵌入方不想污染日志时用）。
- 环境变量 `LIBXCP_PERF_WINDOW_MS=0` 等价于关闭。

## 9. 开销估算

| 项 | 估算 | 占比 |
| --- | --- | --- |
| `steady_clock::now()`（Windows QPC） | ≈20–30 ns | — |
| poll 每 tick 7 次 | ≈0.2 µs | 20 ms 周期的 0.001% |
| DAQ 每帧 7 次（1 kHz） | ≈0.2 µs/帧 = 0.2 ms/s | 0.02% |
| `Record()` 每次 | 数十 ns + slowest 线性查找（k≤5） | 可忽略 |
| 窗口格式化 | 每 5 s 一次，约数十 µs | 可忽略 |

`sample_every` 是给"DAQ 高频 + 低配机器"的逃生口：设 16 后采样开销降到 1/16，代价是 p95 样本变少（5 s × 1000/16 = 312 个，仍够用）。

## 11. 测试计划

1. **配置生效**：`window=100ms` 时 1 s 内产出约 10 块日志；`slowest_capacity=0` 时无 `slowest` 行；`verbose_stages=false` 时只有 `total`。
2. **采样率**：`sample_every=4` 下 `count == frames/4`（±1），且 `E2e` 只统计被采样的帧。
3. **窗口语义**：假时钟推进，断言窗口边界、`TakeSnapshot` 后归零、桶计数之和 == `count`。
4. **加和性**：假数据库 `ToPhysical` 固定 sleep，断言 `sum(阶段) ≈ total`（误差 <5%）。
5. **slowest 正确性**：构造 10 个已知耗时，断言 top-3 顺序、`n`/`sum`/`max`/占比正确，跨阶段同名变量各占一槽。
6. **开销不退化**：复用 `tests/poll_capacity_calibration.cpp` 场景，开关两态容量差 ≤5%。
7. **日志频率**：跑 10 s 断言约 2 块日志、且无逐 tick 日志。
8. **环境变量**：合法值生效、非法值回落缺省且不抛。
9. **不变量回归**：超期率 ≤1%、平均周期偏差 ≤5%、`read_errors == 0`。
10. **字节量聚合**：构造 3 个已知大小的合并组，断言 `group_bytes_total` == 各组 `byte_count` 之和、`group_bytes_max` 正确、`group_slices_total` == 参与合并的变量数；`group_size` / `group_bytes` 正确落到 `group_read` 的 slowest 槽。
11. **合并与类型无关**：`U8`+`U32` 相邻地址必须合并成一组（回归 §5.1 的结论）。

## 13. 已知限制

1. 分位数是**桶内插值近似**，只能用于找热点，不能当精确 SLA 数字；
2. `E2e` 依赖队列元素加时间戳，队列容量不变但元素变大（每元素 +8 B）；
3. 多 event 场景下窗口是**整个会话**的，不是每 event 一块日志——需要按 event 细分时另加维度（本计划不做）；
4. 未采样帧的耗时不可知，`sample_every > 1` 时统计是抽样估计；
5. 统计不跨线程合并：poll 与 DAQ 各自独立窗口；
6. 字节量只统计**合并组读取**；合并组失败后回退的单读字节另记 `single_read_bytes`，不混入 `group_bytes_total`，避免把回退读算进合并收益。

## 14. 验收标准

1. 默认参数下 poll 20 ms 跑 10 s，恰好产出约 2 块日志，包含 total/阶段/slowest/hottest；
2. `SetPerfConfig({.window=1000ms})` 后日志频率立即变化，且不影响读取正确性（既有用例全绿）；
3. 关闭统计后 `poll_capacity_calibration` 的容量与开启时差 ≤5%；
4. 全部新增接口有 doxygen 中文注释，新增测试进 `tests/CMakeLists.txt` 并被 `ctest` 发现；
5. 日志首部能看到 `bytes/tick`、`group_mean`、`group_max`，`group_read` 行下方有 `vars/group` 与 `bytes/group`；
6. `group_read` 的 slowest 槽带 "组 N 变量 / M B" 标注，且 `N`、`M` 与提前构造的 A2L 布局一致；
7. 全量 `ctest` 0 失败。
