## 1. P1：UDP 按报文边界推导 Tail

### 1.1 为什么必须做

`UdpTransport` 此前要求调用方给出 `packet_alignment`，收包用 `DecodeUdpDatagramAligned(payload, alignment)`：
按 **给定对齐** 计算每帧之后的填充长度。对端若按"自身对齐"补白，而调用方声明值不同，
第二帧起就会错位——且错位是**静默**的（解析出的长度恰好自洽）。

关键洞察：UDP 的报文边界本身就是"最后一帧结束位置"的证据。
TL V1.5 §4.3.2.1 允许发送方**不填充**最后一个 Packet，
于是"datagram 实际长度 − 各帧已知长度"只剩 0..3 字节的尾部填充，
完全可以从数据本身推出来，不需要任何先验声明。

### 1.2 实现

```cpp
[[nodiscard]] std::optional<std::vector<EthernetFrameView>>
DecodeEthernetDatagramByBoundary(BytesView datagram,
                                 std::uint8_t max_tail = 3) noexcept;
```

- 中间帧：`tail = 0`（Tail 只可能出现在最后一帧之后）。
- 最后一帧：`tail = 剩余字节数`，但仅当 `0 ≤ 剩余 ≤ max_tail`；否则判整条报文非法。
- 保留原 `DecodeEthernetDatagramAligned` 不动：它仍是 V1.5 严格语义的**发送侧/严格收侧**入口，也是既有测试的断言对象。
- `UdpTransport` 侧改为：边界推导解码 → 若调用方声明了对齐，再逐帧核算 `TailBytesForAlignment` 是否与推导值一致，不一致记一条告警（诊断用，不阻断）。

### 1.3 行为变化（对调用方可见）

| 场景 | 改前 | 改后 |
|---|---|---|
| 调用方未给 `packet_alignment` | `Open()` 抛 `InvalidArgument` | 正常建链，按边界推导 |
| 对端补白与声明值不符 | 静默错位 / 解析失败 | 正常解析 + 一条告警 |
| 接收侧超出 3 字节的多余尾部 | 取决于声明值 | 判非法（`nullopt`） |

发送侧同时去掉补白：`EncodeUdpFrame(packet, ctr)`（:598）——不补白是本库作为 Master 的既有行为，
本次只是补上了"收到不补白报文也能正确解析"的另一半。

## 2. P2：版本参数降级 + A2L 证据接入

### 2.1 问题

`VersionPolicy.protocol_version` / `transport_version` 此前是**必填式**语义：
CLI 未给时，对端若不实现 GET_VERSION（XCPlite V1.2 就是），最终只能落到 `1.x-conservative`，
把已知的 1.2 / 1.4 低估成 1.3 交集。

### 2.2 实现

```cpp
std::optional<XcpProtocolVersion> a2l_protocol_version;   // protocol_version.hpp:336
std::optional<XcpProtocolVersion> a2l_transport_version;  // :341
```

优先级（`src/version_resolver.cpp`）：调用方显式配置 > A2L 静态证据 > CONNECT 主版本 > 保守下限。

同时补掉一个死字段缺陷：`ProtocolVersionSnapshot::conflicts_with_a2l` /
`TransportVersionSnapshot::conflicts_with_a2l` 早已声明，但全仓从未赋值——
即便 A2L 与实测版本矛盾也不会有任何提示。现在由 `VersionResolver::Resolve` 根据
"A2L 值可用且与最终 reported 不等"置位（不参与取值优先级，只做诊断）。

### 2.3 实测

连 XCPlite V1.2 从站（`--transport udp`，该从站无 GET_VERSION）：

```
PL: reported=1.2 source=A2l effective=1.2 conservative=0
TL: reported=1.4 source=A2l effective=1.4 conservative=0
conflicts=0
```

改前同样的对端只会得到 `1.x-conservative`。

## 3. P3：TCP 帧布局连接级候选试连

### 3.1 为什么不许"连接内嗅探"

`AsamV14` 与 `AsamV15` 在 `PACKET_ALIGNMENT_8` 下**字节完全相同**，任何基于首帧内容的猜测
在边界条件下都会静默吞掉下一帧的 Header。因此在同一条连接里切换 Profile 是禁止项
（文档已在 `tcp_wire_profile.hpp` 中写明）。

允许的唯一自动化形式是**连接级**试连：每个候选用全新连接试一次，失败即断开，不污染已有流。

### 3.2 库内机制（`tcp_framing_negotiation.hpp`）

```cpp
struct TcpFramingCandidate { TcpWireProfile profile; PacketAlignment alignment; };
std::vector<TcpFramingCandidate> DefaultFramingCandidates();  // 固定顺序
using FramingAttemptFn = std::function<bool(const TcpFramingCandidate&, std::string*)>;
TcpFramingNegotiationResult NegotiateTcpFraming(const std::vector<TcpFramingCandidate>&,
                                                const FramingAttemptFn&);
```

候选阶梯（顺序是契约的一部分）：

1. `AsamV14 / 8bit`
2. `AsamV15 / 8bit`
3. `AsamV15 / 16bit`
4. `AsamV15 / 32bit`

先 8 bit 是因为兼容面最大；`V14` 先于 `V15` 是因为 8 bit 下两者字节相同、而 V1.4 的 CTR 语义更宽松。
非 8 bit 只可能是 V1.5（V1.4 没有 LEN 外 Tail）。

机制只负责**顺序、预算、记录**，判定语义全部由调用方注入的谓词决定——这样库不掺和
"什么叫连上了"的业务判断。

### 3.3 CLI 侧

- `--tcp-profile auto`：显式开启，绝不因为"用户没写"而自动开启。
- 谓词实现：每个候选构造 `TcpTransport` + `XcpMaster`，`Connect()` 后做**域内校验**
  （`src/../tools/xcp_master/main.cpp` 协商循环）：
  - `MAX_CTO ∈ [8, 255]`、`MAX_DTO ∈ [8, 65535]`；
  - CONNECT 回报的 PL 主版本 = 1、TL 主版本 = 1。
  只校验"帧能解析"是不够的：完全无关的服务端也可能恰好吐出长度自洽的字节。
- 胜出者**直接留用**，不做二次连接：`XcpMaster` 没有移动构造，所以统一改成
  `std::unique_ptr<XcpMaster>` 持有。
- 互斥规则（`transport_selection.hpp` 规则 8）：
  - 非 TCP → 报错；
  - 与 `--preset xcplite` → 报错（preset 已固定 asam-v1.4）；
  - 与 `--packet-alignment` → 报错（对齐由候选决定）；
  - 与具体 `--tcp-profile` → 报错。
- `auto` 生效时 `wire_profile` / `alignment` 保持 `Unknown`，**不给任何默认值**：
  否则调用方会跳过试连直接用默认 Profile 建连，`auto` 就退化成静默猜测。

### 3.4 实测

**真实从站（XCPlite V1.2，TCP 5651）**

```
TCP 帧布局协商成功：profile=AsamV14 alignment=8bit（第 1 次尝试，累计 3 ms）
```

**无监听端口（5699）**

```
TCP 帧布局协商失败：全部 4 个候选均不可用
  · profile=AsamV14 alignment=8bit：连接远端失败: 127.0.0.1:5699
  · profile=AsamV15 alignment=8bit：连接远端失败: 127.0.0.1:5699
  · profile=AsamV15 alignment=16bit：连接远端失败: 127.0.0.1:5699
  · profile=AsamV15 alignment=32bit：连接远端失败: 127.0.0.1:5699
```

最坏代价因此是可观测的：4 次连接，每次受 `connect_timeout_ms` 约束。

## 5. 与计划的偏离

1. **P1 未实现"中间帧 Tail 试探"**：计划 §4.4 就写明不做——试探等于嗅探，且中间帧补白在
   AsamV15 语义里根本不该存在。实现严格按此执行。
2. **`FramingCandidateName` 使用库内枚举名**（`AsamV14/8bit`）而不是 CLI 拼写
   （`asam-v1.4/8bit`）：库不该复制 CLI 词汇表；摘要文本改为 `profile=... alignment=...`
   便于日志检索。
3. **CLI 侧接受最坏 4 次连接、不设 2 次上限**：按用户裁决（m05767）执行。
4. **`selection` 不回写**：`ResolveTransportSelection` 返回的是 `Result` 视图（`operator->` 为
   const），胜出配置只写回 `options->transport_request.packet_alignment_bits` 供日志使用。
   计划 §6 里"回填 selection"的措辞在实现时改为"回填 Options"，避免两处状态不一致。

## 6. 未验证项 / 已知限制

1. **CLI 端到端未跑**：`xcp_master` 在 A2L 加载**之前**就检查 `IsInteractiveTerminal()`，
   本环境无法构造伪终端（`pty.openpty()` 报 `out of pty devices`）。因此
   `--tcp-profile auto` 的完整 CLI 流程只有纯函数层（31 个选择规则用例）与库级探针覆盖。
2. **仅 macOS 验证**：Windows/Linux 未构建。P3 机制本身是纯标准库，风险集中在 CLI 接线。
3. **未验证"对端只支持 16/32 bit"的真实场景**：候选阶梯的后两级没有真实对端可测，
   仅由单元测试保证顺序与调用次数。
4. **8 bit 歧义未消除**：`AsamV14/8bit` 与 `AsamV15/8bit` 字节相同，实际总选前者；
   两者的差异只体现在 CTR 宽松性上。这是设计上的已知取舍，不是缺陷。
