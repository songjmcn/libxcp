# 发布门批次 3：接收语义与帧定界修复记录

> 对应发布门条目：**A-02**（UDP 一次 ICMP 永久终止接收线程）、**M-03**（测试把该行为写成期望）、**T-02**（一个超限帧拖垮整条 TCP 连接）。
> 依据 `docs/review/ARBITER-1-transport-concurrency-security.md` 与用户批准的「4 批次」方案（批次 3 = A-02 + M-03 + T-02 同批改）。

## 1. 缺陷回顾

### 1.1 T-02：超限帧导致 TCP 连接永久终止

`TcpTransport::Open()` 用 `min(max_packet_size, max_frame_packet_size)` 构造 decoder。于是"LEN 合法但超过 `max_frame_packet_size`"的帧会在 decoder 内部被判为**流已失步**并停机，接收线程随后以畸形原因关闭连接——其后所有合法帧都被丢弃。

而 `src/tcp_transport.cpp` 的接收线程里本来就有"该帧已丢弃"分支（丢弃单帧并告警），只是永远不可达。一个超限帧不该拖垮整条流。

### 1.2 A-02：UDP 一次 ICMP 就被判成"连接丢失"

Windows 上未连接的 UDP 套接字收到 ICMP port unreachable 后，下一次 `recvfrom` 返回 `WSAECONNRESET`。`IsConnectionLostCode()` 把它归入"连接丢失"，接收线程据此以 `Socket 已关闭或失效，接收线程退出` 永久退出——但 UDP 没有连接语义，这类错误应当被忽略。POSIX 不会投递该错误，因此还造成 Windows/POSIX 行为不一致。

### 1.3 M-03：测试把错误行为固化成期望

`tests/udp_transport_test.cpp` 的 `ConnectionLostStopsReceiveLoop` 断言"一次 ICMP 后连接关闭"，等于把缺陷写成了验收标准——修复 A-02 反而会让 CI 变红。

## 2. 修改内容

### 2.1 T-02：decoder 只定界，超限帧由接收线程丢弃

`src/tcp_transport.cpp`（`Open()`）：

```cpp
// 改前
const std::size_t decoder_limit =
    (std::min)(m_config_.max_packet_size, m_config_.max_frame_packet_size);
// 改后
const std::size_t decoder_limit =
    (std::max)(m_config_.max_packet_size, m_config_.max_frame_packet_size);
```

- decoder 的职责收窄为**按 LEN 定界**（防止缓冲无界增长），"这一帧要不要交付"由接收线程按 `max_frame_packet_size` 判定。
- 取较大值保证：只要 LEN 不超过任一配置上限，decoder 都不会停机；超限帧按 LEN 正常定界后被丢弃。
- `src/tcp_transport.cpp` 原有分支「Frame 内 XCP Packet 长度 … 超过配置上限，该 Frame 已丢弃」由此变为**可达**，无需新增代码。

### 2.2 A-02：关闭 Windows 上的 ICMP 错误上报

`src/detail/socket/socket_ops.hpp` 新增非纯虚接口（基类直接返回成功，POSIX 与测试替身无需实现）：

```cpp
virtual int disable_udp_icmp_error_reporting(SocketHandle handle);
```

`src/detail/socket/socket_ops_win.cpp` 实现：

```cpp
BOOL disable = FALSE;
DWORD returned = 0;
return ::WSAIoctl(ToNative(handle), SIO_UDP_CONNRESET, &disable, sizeof(disable),
                  nullptr, 0, &returned, nullptr, nullptr) == 0 ? 0 : -1;
```

- 旧 SDK 未定义 `SIO_UDP_CONNRESET` 时按官方定义补 `#define SIO_UDP_CONNRESET _WSAIOW(IOC_VENDOR, 12)`（本机构建即触发该分支）。
- `src/udp_transport.cpp` 的 `Open()` 在创建 socket 后调用；**失败不致命**，仅告警，因为接收循环已能容忍该错误。

### 2.3 A-02：连接丢失降级为可恢复错误

`src/udp_transport.cpp` 的 `ReceiveLoop()`：

```cpp
// 改前
if (invalid || connection_lost) { close_reason = "Socket 已关闭或失效…"; break; }
// 改后
if (invalid) { close_reason = "Socket 已关闭或失效…"; break; }
```

`connection_lost` 落入既有的"限频告警 + 退避后继续接收"分支，告警文本区分成因：
`（ICMP 端口不可达/连接重置，已忽略并继续接收）`。

### 2.4 M-03：用例改向

`tests/udp_transport_test.cpp`：`ConnectionLostStopsReceiveLoop`（断言关闭）改为 `ConnectionLostWarnsAndContinues`（断言告警一条、`IsOpen()` 为真、不得交付关闭事件）。

## 6. 已知问题（不在本批次范围）

`XcpSlaveDemoIntegrationTest.CrossProcessCalibrationChangesDaqOutput` 存在**既有偶发失败**（约 1/10）：`START_STOP_DAQ_LIST 响应长度不足（RES 数据 0 字节，期望 >= 1）`。

已用对照实验确认与本批次改动无关：把批次 3 的两处 UDP 改动临时回退后连跑 10 次，仍失败 1 次（同样错误）。该偶发属于用户此前反馈的"丢帧问题未完全解决"，需要单独定位，不与本次发布门修复混在一起。
