## 1. 本批范围

| 命令 | 码 | 规范类别 | 本批交付 |
| --- | --- | --- | --- |
| DOWNLOAD（块模式） | 0xF0 | Mandatory for CAL/PAG | 块首帧发送（不应答） |
| DOWNLOAD_NEXT | 0xEF | Optional | 中间帧（不应答）与末帧（等应答） |
| DOWNLOAD_MAX | 0xEE | Optional | 固定满帧写入，与 DOWNLOAD 不同的对齐规则 |
| SET_REQUEST | 0xF9 | Optional | STORE_CAL_REQ 请求 + GET_STATUS 轮询确认 |
| BUILD_CHECKSUM | 0xF3 | Optional | 目标端 checksum 取回 + 本地核对 |

配套业务入口：`MemoryAccess::VerifyBytes`（写后校验）、`MemoryAccess::RequestCalibrationStore`（持久化请求），以及 `MemoryAccess::SetBlockModeEnabled`（块传输显式开关）。

明确排除（不在本批）：
- STIM 方向数据下发；
- 编程（`PROGRAM_*`）与 `PROGRAM_RESET`；
- `DOWNLOAD_NEXT` 的 `ERR_SEQUENCE` 自动续传重排（见 §6 遗留）。

## 2. 规范要点核对

### 2.1 块传输语义（决定实现形态）

- `DOWNLOAD` 的 n 是**本次块的总元素数**；`DOWNLOAD_NEXT` 的 n 是**剩余元素数（含本帧）**。
- 额外帧数：`AG = 1` 时 `((n*AG)-1)/(MAX_CTO-2)`，`AG > 1` 时 `((n*AG)-1)/(MAX_CTO-AG)`。
- **只有末帧被肯定应答**，中间帧没有 RESPONSE；Slave 仍可在块中即时回负响应。
- `DOWNLOAD_MAX` 对齐规则与 `DOWNLOAD` **不同**：Table 85 标注对齐字节仅当 `AG > 1` 存在，元素 1 位于偏移 `AG`，故对齐字节数 = `AG-1`（BYTE 0、WORD 1、DWORD 3）；整帧长度恒等于 `MAX_CTO`，数据 = `MAX_CTO-AG` 字节 = `MAX_CTO/AG-1` 元素。
- `DOWNLOAD_MAX` **不支持块传输，且不得出现在块传输序列中**，每帧必须应答。

### 2.2 SET_REQUEST 与 BUILD_CHECKSUM

- `SET_REQUEST` CTO = `[0xF9][Mode][WORD Session configuration id]`；`STORE_CAL_REQ` 是 Mode bit0。规范**没有给正响应参数表**，因此正响应只校验 `0xFF`，不解析任何参数字节。
- `STORE_CAL_REQ` 由 Slave 在**请求完成时**清除 `GET_STATUS` 中的该位，可能伴随 `EV_STORE_CAL`。故"命令被接受"只能判 `Pending`，请求位清除才算 `Completed`。
- `BUILD_CHECKSUM` CTO = `[0xF3][reserved BYTE][reserved WORD][DWORD Block size]`，MTA 后置递增 block size；正响应 = `[0xFF][Checksum type][Reserved WORD][Checksum DWORD]`，结果**恒为 DWORD**。
- 类型表：`0x01..0x06` 为 `XCP_ADD_11/12/14/22/24/44`，`0x07 XCP_CRC_16`，`0x08 XCP_CRC_16_CITT`，`0x09 XCP_CRC_32`，`0xFF XCP_USER_DEFINED`。
- Table 77 只为 `XCP_CRC_16`（poly 0x8005 / init 0x0000 / refin·refout TRUE / xorout 0x0000）与 `XCP_CRC16_CITT`（poly 0x1021 / init 0xFFFF / refin·refout FALSE / xorout 0x0000）给出参数。

## 3. 代码变更

### 3.1 新增模块：checksum

| 文件 | 内容 |
| --- | --- |
| `include/libxcp/checksum.hpp` | `std::optional<std::uint32_t> ComputeXcpChecksum(CalibrationChecksumType, std::span<const std::uint8_t>)` |
| `src/checksum.cpp` | ADD_11/12/14、CRC_16、CRC_16_CITT 实现 |
| `CMakeLists.txt` | `src/checksum.cpp` 加入库源文件 |

可算类型与不可算类型（**返回 `nullopt`，不猜**）：

| 类型 | 状态 | 理由 |
| --- | --- | --- |
| `XCP_ADD_11` / `ADD_12` / `ADD_14` | 可算 | 按字节累加，模 `2^8 / 2^16 / 2^32`，与字节序无关 |
| `XCP_CRC_16` | 可算 | Table 77 参数齐全（等价 CRC-16/ARC，`"123456789"` = `0xBB3D`） |
| `XCP_CRC_16_CITT` | 可算 | Table 77 参数齐全（等价 CCITT-FALSE，`"123456789"` = `0x29B1`） |
| `XCP_ADD_22` / `ADD_24` / `ADD_44` | `nullopt` | 多字节字累加依赖 Slave 字节序，规范未约定 |
| `XCP_CRC_32` | `nullopt` | Table 77 未给出 poly/init/refin/refout |
| `XCP_USER_DEFINED` | `nullopt` | 算法定义在 ASAM MCD-2 MC 外部文件 |

`nullopt` 不是"校验失败"，而是"本地无法独立复算"——调用方必须据此降级为读回（`Indeterminate`/`Readback`），绝不能当作 `Match`。

### 3.2 协议层

| 文件 | 变更 |
| --- | --- |
| `include/libxcp/protocol_types.hpp` | 新增 `enum class CalibrationChecksumType`、`enum class SetRequestModeBit`、`ChecksumTypeName()`、`ToChecksumType()`、`HasSetRequestMode()` 及 `operator|` |
| `src/protocol_types.cpp` | `ChecksumTypeName()`、`ToChecksumType()` 实现（未知类型回 `XCP_CHECKSUM_UNKNOWN`） |

### 3.3 Codec

| 方法 | CTO 形态 |
| --- | --- |
| `EncodeDownloadNext(ElementCount, BytesView)` | `[0xEF][n 剩余元素数][对齐字节(AG>2 时)][data]`，对齐复用 `DownloadAlignmentBytes()` |
| `EncodeDownloadMax(BytesView, std::size_t max_cto)` | `[0xEE][对齐字节(AG-1 个)][data]`；校验 `max_cto % AG == 0` 且 `data.size() == max_cto-AG` |
| `EncodeSetRequest(SetRequestModeBit, std::uint16_t)` | `[0xF9][Mode][WORD Session configuration id]`；拒绝 `mode == 0` |
| `EncodeBuildChecksum(std::uint32_t)` | `[0xF3][reserved][WORD reserved][DWORD block size]`；拒绝 `block_size == 0` |

`DOWNLOAD_MAX` 刻意**不**复用 `DownloadAlignmentBytes()`——规范对两条命令的对齐字节数定义不同，复用会把 DWORD 少填 2 个字节。

### 3.4 Parser

`struct BuildChecksumResponse { std::optional<CalibrationChecksumType> checksum_type; std::uint8_t raw_checksum_type; std::uint16_t reserved; std::uint32_t checksum; }`，`ParseBuildChecksum(BytesView)` 最小 RES 长度 7 字节；短帧返回 `nullopt`，未知类型**保留原始字节**并把 `checksum_type` 置空。

### 3.5 Executor

| 方法 | 发送方式 | 语义 |
| --- | --- | --- |
| `ExecuteDownloadBlockHead(ElementCount, BytesView)` | `SendFrameNoResponse(Download, ...)` | 块首帧，n 报整块元素数，不等应答 |
| `ExecuteDownloadNextFrame(ElementCount, BytesView)` | `SendFrameNoResponse(DownloadNext, ...)` | 中间帧，不等应答 |
| `ExecuteDownloadNextTail(ElementCount, BytesView)` | `RunCommand(DownloadNext, ...)` | 末帧，等应答 |
| `ExecuteDownloadMax(BytesView)` | `RunCommand(DownloadMax, ...)` | 固定满帧，必须应答 |
| `ExecuteBuildChecksum(std::uint32_t)` | `RunCommand(BuildChecksum, ...)` | `ERR_CMD_UNKNOWN` → `nullopt` |
| `ExecuteSetRequest(SetRequestModeBit, std::uint16_t)` | `RunCommand(SetRequest, ...)` | `ERR_CMD_UNKNOWN` → 抛 `UnsupportedFeature` |

私有 `SendFrameNoResponse(CommandCode, BytesView)`：`MarkCommandSent` → `Send` → `ClearPendingCommand`，异常时**先释放 pending 槽位再抛出**，避免后续命令被误判为并发。

`HasUnknownOutcomeOnTimeout()` 与 `NonReplayableCommandName()` 加入 `DownloadNext` / `DownloadMax` / `BuildChecksum`：这些命令超时后**不能自动重放**（可能已部分写入），必须报"结果未知"。

## 4. 关键设计决策

### 4.1 块传输默认关闭（本批最重要的取舍）

初版实现按"能力齐备即自动走块序列"落地，全量测试立即暴露回归：`tests/xcp_daq_test.cpp` 的 `DaqSlave` 在 CONNECT 中把 `COMM_MODE_BASIC` 置为 `0xC0`（含 bit6 `SLAVE_BLOCK_MODE`），但它并不实现 `DOWNLOAD_NEXT`，于是自动块传让对端回 `ERR_CMD_SYNTAX`。

追根因后确认这不是"改测试阈值"能解决的问题：`XcpDaqWrite.ChunkLimitUsesMaxCtoMinusTwo` 恰恰在验证**每块都显式 `SET_MTA`、不依赖 Slave 的 MTA 自增**这一既有安全设计。自动块传与该设计正面冲突。

因此改为 `SetBlockModeEnabled(bool)` 显式开关，**默认 `false`**，理由：

1. 块序列依赖 Slave 逐帧自增 MTA，中间帧没有应答——丢一帧后续数据会静默落到错误地址，主站无法从协议层察觉。
2. 逐块 `SET_MTA + DOWNLOAD` 每块重新落地址，多一次往返，但超时/断连后可安全重试。
3. 默认关闭保证既有行为零变化，块能力作为可选优化由调用方显式承担风险。

开启后仍会检查 `SLAVE_BLOCK_MODE` 与 `MAX_BS >= 1`；协商不满足照样退回逐块通路，不会因为"开了开关"就强行走块序列。

### 4.2 DOWNLOAD_MAX 不参与块序列

规范明文禁止 `DOWNLOAD_MAX` 出现在块传输序列中。本批只把它实现为独立写入通路，`DownloadBlock()` 内部不使用它——即使它能装下更多元素。

### 4.3 checksum 算不出时绝不判 Match

`VerifyBytes` 的判定顺序：类型已知且本地可算 → 比 `slave_checksum` 与 `local_checksum`；类型未知或本地算不出 → **打 warning 转读回**；读回本身抛异常 → `Indeterminate`。

`Indeterminate` 与 `Mismatch` 语义严格区分：前者是"无法判断"，后者是"确定不一致"。调用方不得把 `Indeterminate` 当作写入成功。

### 4.4 持久化只承认 GET_STATUS 可见证据

`RequestCalibrationStore` 的三态严格按规范推导：

- `SET_REQUEST` 被接受 → 最多 `Pending`（Slave 可能还在写 Flash）；
- `GET_STATUS.store_cal_req` 位清除 → `Completed`；
- 轮询超时 → `Pending`；轮询/连接异常 → `Unknown`。

`EV_STORE_CAL` 只作为提示信号，不作为完成证据。

## 6. 边界与遗留

1. **`ERR_SEQUENCE` 续传未实现**：`DOWNLOAD_NEXT` 回 `ERR_SEQUENCE` 时规范允许带"期望元素数"续传。当前实现把该负响应当作普通错误抛出，交由调用方重试整块。理由是自动续传需要精确重建帧边界，做错反而破坏 MTA 一致性，留待后续批次。
2. **`DOWNLOAD_NEXT` 中间帧无应答 ⇒ 无逐帧确认**：块内若 Slave 悄悄丢帧，主站只能靠末帧的负响应或后续写后校验发现。这也是 §4.1 默认关闭的核心理由。
3. **checksum 覆盖范围以 MTA 为准**：`VerifyBytes` 用 `SET_MTA` 定位后调 `BUILD_CHECKSUM`，不做分块累加，因此一次校验的字节数受限（Slave 最大块）；超出部分由调用方分段校验。
4. **`XCP_CRC_32` / `XCP_ADD_2x` / `XCP_ADD_4x` 未支持本地计算**：规范未给足参数，需 ASAM MCD-2 MC 中 `IF_DATA XCP` 的 `CHECKSUM_*` 声明补齐后才能启用。当前统一降级为读回。
5. **写后校验不能替代持久化**：`VerifyBytes` 只证明 RAM 中的目标端数据与预期一致；能否在断电后保持必须走 `RequestCalibrationStore`。
6. **块大小上限取 `min(255, max_bs × 单帧元素数)`**：255 来自 `DOWNLOAD` 的 n 为单字节字段；`max_bs` 是 MAX_BS × MIN_ST 意义上的接收预算，两者取小是保守合并。
