# XCP Master TUI Tool

`xcp_master` is a standalone C++20 terminal UI tool targeting Windows, Linux, and macOS. It browses an A2L database and connects to an XCP-on-UDP or XCP-on-TCP slave. Its display panel and command input are separated; asynchronous polling/DAQ output is routed to the UI rather than printed over active input. It does not launch or depend on XCPlite `cpp_demo` and does not reuse source code from `examples/`. Full platform builds still depend on a Boost/A2L toolchain whose C++ ABI matches the compiler.

## Build

```powershell
cmake -S . -B build -DLIBXCP_BUILD_TOOLS=ON -DLIBXCP_BUILD_TESTS=ON
cmake --build build --config Release --target xcp_master
ctest --test-dir build -C Release --output-on-failure
```

Disable the tool with `-DLIBXCP_BUILD_TOOLS=OFF` (the default). This option is independent of `LIBXCP_BUILD_EXAMPLES` and does not enable XCPlite. When tools are enabled, CMake fetches FTXUI v7.0.3 at a pinned commit using FetchContent; it is not a submodule and is not stored in `thirdparty/`. For offline builds, set CMake's standard `FETCHCONTENT_SOURCE_DIR_FTXUI` override to a matching local checkout. The A2L bridge runtime library is copied beside the executable by the tool target. The project-owned `thirdparty/a2l-sdk` integration explicitly links Boost.Locale and uses it for A2L log timestamps; provide a Boost package built for the same compiler ABI.

## Run

```text
xcp_master --a2l <path> [--host <IPv4> --port <1..65535>] [--transport udp|tcp] [--tcp-profile asam-v1.4|asam-v1.5|auto|auto-legacy] [--packet-alignment 8|16|32] [--module <name>] [--mode poll|daq] [--interval-ms <ms>] [--preset xcplite] [--a2l-trusted-snapshot-root <dir>]
```

The A2L file is required. TCP may use an IPv4 endpoint from command-line options or a matching A2L transport declaration; UDP requires an explicit endpoint. `--module` filters the symbol listing. The default is `--mode poll`; the poll target interval is 500 ms. `--interval-ms` is rejected in DAQ mode; DAQ timing is controlled by ECU events. The DAQ DTO layout is selected from the slave's reported capabilities; there is no `--daq-profile` option. Use `--help` for the current transport options.

TCP `auto` stops before connecting when candidates are ambiguous; a successful CONNECT cannot uniquely identify the wire profile. `auto-legacy` explicitly opts into the previous first-success attempts, which can affect the ECU session and do not establish a unique profile.

For TCP the tool stages the A2L into a private snapshot before the SDK parses it (`--a2l-trusted-snapshot-root`, default `<exe dir>/tmp`) and only trusts the A2L alignment when the restricted raw-text scan and the SDK endpoint facts agree. The snapshot root and every ancestor must be writable only by the current user (plus SYSTEM/Administrators); if that cannot be proven — for example on a tree that grants `Users:(F)` — the tool prints `A2L 受控快照不可信: <reason>` and keeps the A2L alignment untrusted. In that case specify `--packet-alignment` for `asam-v1.5`. This conservative limitation does not change UDP.

### Reusable pieces

The three decisions above are library components, not tool-private code, so other callers can reuse them without the tool's include path:

| Header | What it decides |
| --- | --- |
| `include/libxcp/transport_selection.hpp` | Which transport/protocol profile to use, given CLI intent, A2L declarations and current connection state |
| `include/libxcp/a2l_tcp_alignment.hpp` | Whether the A2L's own TCP endpoint declaration can be trusted as packet-alignment evidence |
| `include/libxcp/trusted_a2l_snapshot.hpp` | Whether an A2L file can be staged into a directory that other identities cannot modify |

They depend only on other `include/libxcp` headers; `tests/transport_selection_standalone_test.cpp` builds against `include/` alone to keep that true.

## Interactive commands

- `list [pattern]`: browse matching A2L names, 40 entries per page. This only queries the A2L database; it does not read live ECU values. The output includes fixed-event declarations.
- `list all`: retain a complete, separately browsable snapshot of all symbols matching the optional module filter in the command-result view (not truncated to the latest 512 diagnostic lines). The next command returns that view to normal results.
- `more`: show the next page from the last listing.
- `info <module::name>`: show symbol metadata, fixed/default/available event lists, and conservative read/write support status.
- `remove <module::name>`: remove a symbol from the observation set. Add or remove the selected symbol from the focused Variables list with F6.
- `read <module::name>`: read a scalar once and convert to a physical value. For a one-dimensional MEASUREMENT array, expand it in the Variables preview and activate its read-once row; the complete vector is read in eight-element chunks and displayed inline. F3 Details never reads the ECU.
- In poll mode, `watch` reads selected symbols immediately and then polls at the requested target interval. The variable preview keeps one latest timestamped snapshot per selected symbol; one-dimensional MEASUREMENT arrays are published as complete batches and can be expanded inline to inspect every element. Stopping preserves snapshots and marks them stopped. Actual cycle time depends on ECU response time and number/size of selected symbols; this is not a hard real-time frequency guarantee.
- In DAQ mode, `watch` uses Slave event-driven DTOs; no polling interval is applied. F6 admits scalar `MEASUREMENT` symbols with exactly one distinct A2L `FIXED_EVENT_LIST` event and a matching A2L `EVENT_CHANNEL`; unsupported rows show an observation rejection reason before selection. In the explicitly selected `xcplite` profile, F6 also admits fixed-length, contiguous one-dimensional `MEASUREMENT` arrays within the static single-Entry limit. For structure measurement leaves (for example, `meas_fast.input` and `meas_fast.samples`), an INSTANCE's fixed event is propagated to its nested measurement leaves in the same module/instance, not guessed from the name. `cal.*` characteristics and all arrays in the `generic` profile remain excluded from DAQ. A `CHARACTERISTIC/VALUE` that is readable in POLL is not automatically eligible for DAQ. Event ID 0 is valid; DEFAULT/AVAILABLE lists are never substituted. `watch` repeats static checks and still validates runtime ECU capabilities; eligibility does not guarantee actual ECU sampling. The `generic` profile supports only the validated, timestamp-free standard Absolute-PID layout, FREE address-extension mode, and one DAQ list. The explicitly selected `xcplite` profile is a separate vendor compatibility path; it validates runtime processor/resolution/event facts and does not imply generic support. Array samples occupy one DAQ Entry and one DTO only: `watch` checks live Entry granularity/maximum length, ODT capacity, layout and address bounds before `FREE_DAQ` confirmation. For the generated `xcp_slave_demo` A2L, `meas_fast.samples` and `meas_slow.history` each contain eight 4-byte elements; expand their preview rows to inspect each complete received array. Eligibility at F6 is static and cannot guarantee that a connected ECU will accept DAQ configuration or produce DTOs. An incompatible generic DTO layout is reported before any destructive DAQ configuration; when the target is known to be XCPlite, restart explicitly with `--daq-profile xcplite`.
- Before each DAQ configuration, the tool performs local layout and capability checks. It then warns that `FREE_DAQ` clears the Slave's entire dynamic DAQ table and requires a fresh `y` confirmation. Refusal sends no destructive configuration command. Existing Slave DAQ configuration is not restored after Stop.
- During DAQ, `read`, `write`, and `remove` are refused; stop first. Observation membership is locked while DAQ is running. After DAQ stops, manual reads and the normal confirmed write/read-back flow are available again.
- `stop` then Enter: stop the active polling or DAQ session. Polling waits for any in-flight XCP command to return or time out.
- `write <module::name> <physical-value>`: request a scalar CHARACTERISTIC/VALUE write. The tool displays current and target values and asks for explicit confirmation; it then writes and reads back.
- `find [pattern]`: search A2L measurements and calibration characteristics; results appear in the unified variable-preview view. Scalar `CHARACTERISTIC/VALUE` and verified fixed-axis `CHARACTERISTIC/CURVE` points may expose write actions; other candidates show their policy reason. The command and preview search box share the active filter when the result is applied. Searching only queries A2L metadata and does not access the ECU.
- `help`, `quit`.

## UI layout and keyboard

The screen has four fixed layers: a two-line status area, the main panel, a persistent command input, and a one-line context hint. The main panel has three horizontal views: **Variables**, **Command results**, and **Logs**. There are no global Watch/Stop/Quit buttons; commands remain available, and F5 requests stop.

The Variables view searches A2L metadata and switches between all candidates and the sampling set. It shows measurements and calibration characteristics; each row includes a compact A2L category, base type, and data-shape label (for example, `MEAS · ULONG · 数组[128]`). Selecting a row does not read the ECU. Enter expands/collapses the selected symbol inline; expanded arrays show every available element in the scrollable list, and an explicit read-once row is available when the symbol is not actively sampled. F3 opens metadata-only details: full symbol name, A2L category, base type, data shape, element width, and static capability reasons. Details do not show live samples or issue ECU requests. One-dimensional MEASUREMENT arrays are observed as complete snapshots in POLL; one-shot reads also update the preview snapshot. F6 toggles observation membership without starting sampling; enter command mode with F7 and run `watch` to start. F4 opens the separate calibration workflow without writing anything until explicit confirmation. Fixed-axis CURVE symbols expose single-point read/write only in the separate calibration view; unsupported axes/layouts remain read-only. Esc closes the current modal step. While a modal is open, background views and the command input cannot receive events.

The UI starts in **preview mode** with focus on the Variables list. Tab/Shift+Tab cycle only among its search box, scope menu, and list; they cannot reach the command input. F2 cycles Variables, Command results, and Logs without changing input mode. In the focused Variables list, Enter expands/collapses a symbol or activates an explicit read-once row; F3 opens read-only details, F4 opens calibration, and F6 adds/removes an observation member. F7 explicitly enters **command mode** from any view. There, ordinary characters are entered as command text, ↑/↓ browse command history, and Enter submits; after a successful submission the command box remains active. Esc leaves command mode without submitting or clearing an unfinished draft, returns to the Variables list, and F7 can reopen that draft. Plain `:`, `m`, and `c` are not operation shortcuts; the previous Ctrl/Command/Alt+A/S bindings are removed. In a modal, navigation and F7 do not reach the background; Esc closes/cancels it, and F5 cancels any pending confirmation before requesting stop. The UI requires an interactive terminal; below 80×24 it keeps command/status areas available but disables variable details and dangerous confirmations. Function keys may be intercepted by OS, terminal, or laptop Fn settings: verify F2–F7 delivery in the target terminal.

Writes still follow the same conservative validation, pre-read, default-cancel confirmation, write, and read-back path as the `write` command. The modal confirmation shows the full symbol and current/target values (or the `FREE_DAQ` consequence/profile). Only `Y/y` confirms; `N/n` or Esc cancels, Enter is not an acceptance, F5 cancels and requests stop, and other input is swallowed. A stop/cancel processed before dispatch revokes authorization; an XCP command already in flight cannot be undone. Ordinary commands are not queued while another is running; a rejected submit keeps its text in the input for retry, while `stop` and `quit` are prioritized. Asynchronous results with an outdated search revision are discarded, preserving the newer draft and current list; valid candidate-list updates are deferred while a modal is open and applied after it closes. Result/log buffers retain at most 512 lines; `list all` uses a separate complete snapshot.

## Safety and capability limits

A2L presence and the A2L `READ_WRITE` flag are metadata, not proof that a connected ECU permits access. Reads/writes are conservatively refused for unknown widths, bit fields, addresses outside the 32-bit XCP range, incompatible address granularity, or A2L/ECU byte-order disagreement. Scalar writes are limited to invertible `CHARACTERISTIC/VALUE`; fixed-axis `CHARACTERISTIC/CURVE` writes are limited to a validated single point. Both require explicit confirmation plus static A2L and runtime XCP page permission. One-dimensional MEASUREMENT arrays can be sampled as complete snapshots in POLL and read once from the expanded preview; each read is transferred in eight-element chunks while the UI displays the entire vector. Details are metadata-only and never issue an ECU request. DAQ arrays are restricted to explicitly selected XCPlite and a validated fixed contiguous one-dimensional MEASUREMENT that fits in one Entry and one DTO; generic-profile arrays and split-ODT arrays remain unsupported. An array DTO is published as a single complete snapshot only after every element converts successfully; failed samples retain the last valid snapshot marked stale. ECU-side protection can still reject writes; the tool does not invent or automatically run a Seed&Key algorithm. The local command mutex cannot prevent the ECU or another XCP master from switching pages between the final permission check and WRITE; post-write checks can detect some changes but cannot undo a write that reached a different page.

DAQ is deliberately not advertised as compatible with arbitrary XCP slaves. Unknown/unverified DTO headers, timestamp modes, missing/ambiguous event declarations, insufficient resources, or mismatched runtime facts are rejected rather than decoded speculatively. The generic profile does not use XCPlite's proprietary DTO marker, first-ODT timestamp convention, or timestamp unit mapping. Contiguous fixed one-dimensional arrays have been verified only in the explicitly selected XCPlite profile with whole-Entry/whole-DTO routing; no generic array support or cross-ODT array reconstruction is implied. Only verified fixed-axis CURVE single points are supported for calibration, not arbitrary curves, MAPs, structures, static PREDEFINED DAQ, page switching, or automatic ECU management. CAN remains outside this tool's supported scope.

Only connect to an ECU for which you have authorization. Use a non-critical calibration value for manual write testing and follow the ECU owner's procedure for restoring it. Automated tests do not constitute validation against every ECU; manual Slave validation is optional and was not part of the build/test suite.
